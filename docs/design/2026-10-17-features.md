# Features

**Scope.** This document covers the features built on top of the core pull, verify, file and
delete pipeline ([frame-lifecycle](2026-10-17-frame-lifecycle.md)). None of them takes part in a
delete decision. They make the archive legible and make the device's state visible: stretched
FITS previews (§1); frame astrometry read from the WCS the ASIAIR embeds (Tier 0, §2); hinted
plate solving with ASTAP for lights that carry no WCS (Tier 1, §3); the live transfer feed (§4);
the next-frame cadence prediction (§5); opt-in correction of the device clock (§6); and the
newer-release indicator (§7). Each
section gives the mechanism, the decisions with their rationale, the rejected alternatives that
explain the shape, and any invariants. This document hosts two series. The clock-sync invariants
I1–I8 (§6.11) are always cited doc-qualified ("features I3"), because three other docs use I1–I8.
The Tier-1 concurrency invariants 1–6 (§3.9) are cited with the section ("features §3.9
invariant 2"). The live-feed decisions 1–7 (§4.1) are design decisions, not invariants; decision
4 keeps the label "d1". Glossary terms (Tier 0, Tier 1, `wcs_status`, sidecar, pending, quiescence,
supersede) are defined in [overview §9](2026-10-17-overview.md).

## 1. FITS previews

A filed frame is opaque until someone opens it in a FITS viewer, and a raw FITS decode looks black,
because the signal sits in a tiny fraction of the sample range. Commander therefore generates an
auto-stretched JPEG for every frame whose bytes are on disk. It shows a thumbnail in every file
list and opens a zoomable viewer on click. A preview is an 8-bit display product, never the
science data. There are no manual stretch controls and no annotation.

The feature uses the word **image** in routes and identifiers (`/api/frames/{frameId}/image`,
`handleFrameImage`, `frameImageUrl`, package `internal/imgpreview`), because "preview" already
names the Settings path-template dry run (`POST /api/config/preview`).

### 1.1 The rendering pipeline

The stretch is a preview-grade approximation of PixInsight's Screen Transfer Function: a
midtones transfer function driven by each channel's median and normalised median absolute
deviation. It makes no attempt at byte parity with any external tool.

**Validate, then decode.** `internal/imgpreview`'s `decode` reads the header first through
`internal/header`'s bounded read of header blocks only, and gates the geometry before any pixel
buffer is allocated:

- `BITPIX` must be one of {8, 16, 32, 64, −32, −64}.
- `NAXIS` must be 2 or 3, with `NAXIS1` and `NAXIS2` greater than zero. For `NAXIS=3`, `NAXIS3`
  must be 1 or 3.
- A **150 MP pixel ceiling** is checked by successive division (`NAXIS1 > ceil/NAXIS2`), so the
  check never forms the product. 150 MP is well above any astro sensor (the largest in the default
  sensor map is about 61 MP) and bounds the transient memory of a `full` render.

Only then does `github.com/astrogo/fitsio` decode the primary HDU, inside a `recover()`, so a
malformed data unit becomes a decode error rather than a panic. A non-image or tile-compressed
primary HDU is an unsupported, deterministic decode error; the ASIAIR writes uncompressed primary
HDUs.

`fitsio`'s `Read` returns raw, unscaled samples. The library rescales only in its `Image()`
convenience method, which this code never calls. The decoder therefore applies
`phys = BSCALE·raw + BZERO` once, by hand, into a slice typed by the FITS sign convention
(`[]uint8` for 8, signed integer slices for 16/32/64, float slices for −32/−64). It then
normalises with `v = clamp01(phys / fullScale)`, where `fullScale` is the unsigned maximum of the
integer depth and 1.0 for floats. 16-bit camera data uses `BZERO=32768`, so an `int16` −32768…32767
maps to 0…65535. Float frames are taken as already in [0,1] and clamped. A non-finite sample maps
to 0.

**Row order and debayer.** The decoded image is planar `float32` in [0,1], top-down. When
`ROWORDER=BOTTOM-UP`, mono and native-RGB planes are flipped. A CFA frame (`BAYERPAT` present,
`NAXIS=2`) is the exception: it is debayered in the order it was **stored**, using `BAYERPAT` as
written (with any `XBAYROFF`/`YBAYROFF` shift), and only the resulting RGB planes are flipped. A
vertical flip of the raw mosaic shifts the Bayer row phase (`RGGB`↔`GBRG`), so flipping first
would swap red and blue. Two demosaics are available:

- **Superpixel.** Each 2×2 quad becomes one RGB pixel, with green the average of the two green
  sites. This yields a half-resolution image with no full-resolution RGB buffer. A dangling odd
  row or column is dropped.
- **Bilinear.** Each missing colour is the average of its nearest same-colour neighbours, with
  indices clamped at the border. This yields a full-resolution RGB image.

Bilinear is used only when the output exceeds half the native size on either axis
(`dw > W/2 || dh > H/2`). Below that, superpixel's half resolution already exceeds the output.

**One stretch for every size.** The stretch parameters come from a **proxy**: the canonical base
(the superpixel planes for a CFA frame, the native planes otherwise) downscaled to 2048 px. Every
size applies those same per-channel parameters, so `thumb`, `card`, `screen` and `full` share one
black point and contrast. A downloaded `full` image therefore looks exactly like the lightbox
view. The statistics sort also stays bounded at ≤ 2048² values. Per channel (unlinked, which also
gives colour frames a rough white balance):

```
med, madn = median(proxy), 1.4826 · MAD(proxy)          // finite samples only
c0        = clamp01(med − 2.8 · madn)                  // shadows clip
m0        = (med − c0) / (1 − c0)
beta      = clamp01( m0·(t−1) / (2·t·m0 − t − m0) ),   t = 0.25 (target background)
out(v)    = mtf(beta, clamp01((v − c0)/(1 − c0)))
mtf(m,x)  = (m−1)·x / ((2m−1)·x − m)   with x≤0→0, x≥1→1, m≤0→1, m≥1→0, x=m→0.5
```

The three constants that define the look are the −2.8 shadows clip, the 0.25 target background
and the 1.4826 MAD normalisation (`internal/imgpreview`, `stf.go`). **Degenerate guard:** a
channel with `1 − c0 ≤ 0`, or with `madn` below 1e-6, passes through **unstretched**. A truly flat
calibration channel therefore renders at its real level (near-black for a dark, mid-grey for a
flat) instead of being crushed to black. A real dark carries read noise, so `madn > 0` and the
normal stretch shows that noise.

**Downscale and encode.** `fitDims` bounds the longer edge, preserves the aspect ratio and never
upscales. The downscale is a fractional-coverage area average, so stars do not alias away at the
non-integer ratios `fitDims` produces. Output is 8-bit (`image.Gray` or `image.NRGBA`), encoded
with `image/jpeg` at quality 85.

### 1.2 Sizes: named and arbitrary

| Size | Longest edge | CFA demosaic (§1.1 rule) | Used by |
|---|---|---|---|
| `thumb` | 256 px | superpixel | list rows (warmed eagerly) |
| `card` | 1024 px | superpixel (bilinear if the output exceeds half native) | the frame detail modal |
| `screen` | 2048 px | superpixel (bilinear if the output exceeds half native) | the lightbox's first view; also the stretch-proxy bound |
| `full` | native | bilinear | lightbox zoom, download, copy |

Named sizes are cached on disk, so the cache holds at most four entries per frame. A request with
numeric `w` and/or `h` is an **arbitrary** render: it is fitted into that box, clamped to native
(never upscaled) and streamed from memory. **It is never cached**, because arbitrary dimensions
would make the cache's cardinality unbounded. The frontend never uses arbitrary sizes; they exist
for API callers.

Precedence is: an explicit `size` wins; otherwise `w`/`h` select an arbitrary render; otherwise
the default is `thumb`. `full` is reachable only by an explicit `size=full`.

### 1.3 The disk cache

```
<data-dir>/previews/<aa>/<bb>/<sha256>/<size>.v1.jpg
<data-dir>/previews/<aa>/<bb>/<sha256>/decode.v1.fail
```

The cache is keyed on the frame's `sha256`, fanned out on its first two byte pairs. `v1`
(`imgpreview.ParamsVersion`) versions the pipeline: bumping it invalidates every old file without
a purge. Duplicate content shares entries, and a frame whose `dest_path` changes (a re-file or
retarget) keeps its previews with no re-render. A supersede ([frame-lifecycle
§11.7](2026-10-17-frame-lifecycle.md)) advances `sha256`, so the revised bytes get their own
entries and their own warm.

**Immutability carries the concurrency.** Every file is written to a temporary file and renamed
into place, and once present it never changes. That property keeps the rest lock-light:

- A named render runs inside `golang.org/x/sync/singleflight`, keyed on `sha256/size`. The shared
  work returns a **path**, never a handle; each caller opens its own handle. Followers share the
  leader's result, including its 8 s-deadline error (§1.4), so a follower can get a 503 without
  ever waiting for a slot itself. That is accepted, because the 503 is retryable.
- If serving loses a race with an eviction, it re-renders once (or 404s).
- The semaphore slot is acquired **inside** the singleflight function, so a follower waiting on a
  leader holds no slot.
- Eviction is a best-effort, non-blocking `RemoveAll` of a digest directory. On POSIX an open
  reader keeps reading valid bytes. On Windows an open file makes the removal fail; the entry
  survives until the next LRU pass or the startup scan.

The in-memory index is advisory. The disk, consulted at serve time, is authoritative.

**Negative cache: deterministic failures only, per digest.** A deterministic decode failure (an
unsupported `BITPIX`/`NAXIS`, geometry over the ceiling, a compressed or non-image HDU, a render
panic) writes one zero-byte `decode.v1.fail` marker, which every size consults. A header that
cannot be read at all, a non-FITS file included, is treated as transient, because it is most often
the file being briefly unreachable. Only a failure to open the file or read its header counts as
transient, such as an unreachable NAS, and writes no marker, or a network blip would poison a
good frame for good. A data-unit read error, including a short or truncated read, counts as
deterministic and writes the marker; the frame's previews stay off until `ParamsVersion` is
bumped. `Warm` never writes a marker: it competes with transfers for the same NAS, so
it is the path most likely to see a transient error.

**Eviction triggers.**

- **Dismiss.** `discardOne` calls `EvictDigest` on the worker goroutine after purging the NAS copy
  ([frame-lifecycle §13](2026-10-17-frame-lifecycle.md)). The purge, and so the eviction, happens
  only when no other live row of the rig shares the `dest_path`; a shared copy and its previews are
  kept. Dismiss is the only transition that removes a filed frame's NAS copy outright. A supersede
  replaces the copy with revised bytes under a new digest, and the old digest's entries are left for
  the LRU cap. A `deleted` frame keeps its NAS copy, and so its previews. Dismissing one frame also
  evicts the shared entry of any identical-content duplicate, which is accepted, because the entry
  is rebuildable.
- **LRU cap.** `preview_cache_max_bytes` (default 2 GiB) bounds the cache. The startup scan
  rebuilds an index of `digest → bytes, last access` (file mtime seeds the last access) and
  deletes orphan temporary files left by a crash. Each render also removes its own temporary file
  on failure. The index's last-access time is updated on every serve, which is what makes the cap
  LRU rather than FIFO. Each write commits its byte count under the index mutex and evicts the
  least-recently-used digests **other than its own**, so an entry larger than the cap is still
  admitted. Together with the 256 MiB validation floor, this rules out a render evicting itself in
  a loop.

### 1.4 The image endpoint

`GET /api/frames/{frameId}/image?size=…` or `?w=&h=` runs under `guardRead` (Host allowlist and
session; an `<img>` GET carries no CSRF token). `GET /api/frames/{frameId}/image/meta` returns the
native `{width, height}` from the header alone, so the lightbox can build its zoom `srcSet`.
`{frameId}` is the int64 frame id, named so that it is distinct from the string rig `{id}`.

1. **Eligibility.** A frame is served only with a non-empty `dest_path` and `sha256`, and a state
   in {verified, deleted, unclassified, held}: the states that keep a NAS copy (`eligibleForImage`).
   Everything else is a 404, which the frontend renders as a placeholder.
2. **Dispatch.** A named size calls `RenderOnDemand`, which returns a cache path. `w`/`h` call
   `RenderResized`, which returns bytes. `w` and `h` parse as non-negative integers. The cache path
   is built from the store's hex `sha256` and the validated size enum, and an arbitrary render
   never forms a path, so there is no traversal surface.
3. **Deadline.** The handler passes an 8 s deadline (`renderDeadline`) for the slot wait. A burst
   of cache misses therefore returns 503 instead of piling connections onto the semaphore. A
   decode failure or a missing file returns 404.
4. **Serve.**
   - Named: served with `http.ServeContent`, `ETag "<sha256>-<size>-v1"` and
     `Cache-Control: private, max-age=31536000, immutable`. A year-long immutable cache is safe
     only because the frontend's URL carries `v=<first 12 hex of sha256>`. Content that changes
     under the same frame id (a re-pull, a supersede) gets a different URL.
   - Arbitrary: `ETag "<sha256>-<w>x<h>-v1"` and `Cache-Control: private`, without `immutable`.
     API callers do not add the content stamp, so revalidation runs on the ETag, which embeds the
     `sha256`.

When previews are disabled the `Previewer` dependency is nil, and both routes return 503: the same
nil-dependency rule as every optional `web.Deps` field.

### 1.5 Why a list page cannot overload the server

A list can hold hundreds of rows. These layers, in the order they cut the load, keep the server
from running hundreds of decodes at once:

| Layer | Effect |
|---|---|
| `loading="lazy"` on every thumbnail | Off-viewport rows do not request. This is the load-bearing brake for History, Recent transfers and Unclassified, which are not virtualised. |
| Virtualised rows (`@tanstack/react-virtual`), Feed only | Off-screen feed rows are not in the DOM. |
| Eager thumbnail warm | Recently filed frames are cache hits. |
| Immutable, content-versioned caching | The browser never re-requests an unchanged frame. |
| Bounded semaphore (`preview_concurrency`) | Misses queue behind a fixed number of decodes, so CPU use is capped whatever the request volume. |
| Singleflight | Concurrent requests for one `(sha256, size)` share one render. |
| Fixed named sizes | Per-frame cache cardinality is bounded. |

**The warm.** When a frame is filed, `recordFiled` (and the supersede path) calls `Warm(sha256,
destPath)` on the worker goroutine. `Warm` only dispatches: a goroutine `TryAcquire`s one slot and,
if it gets one, renders the thumbnail directly. It never enters the singleflight, so a render never
acquires twice and cannot wedge at `preview_concurrency=1`. If the pool is busy, the warm is
skipped; the on-demand path covers the frame later. The image endpoint is authoritative (§1.4): the
warm is only a cache pre-fill, so a skipped or failed warm can never cause a missing preview. A warm
racing an on-demand render of the same thumbnail can produce at most one duplicate render, with
identical bytes and an atomic rename. The warm goroutine is panic-isolated.

The warm is not gated by transfer admission ([frame-lifecycle §5.1](2026-10-17-frame-lifecycle.md)),
only by the preview semaphore. That is why it uses a try-acquire: it yields to active transfers on
the NAS instead of competing with them.

**Memory weights.** Decode buffers scale with the sensor, not the output. Even a thumbnail of a
61 MP frame holds a full-resolution `float32` plane (about 244 MB) plus the raw slice. A `full`
bilinear render adds a three-plane buffer and the `NRGBA` output, for a transient total of about
1.3 GB. Renders likely to take the full-resolution path therefore acquire a heavy weight of
`min(2, preview_concurrency)`, which never exceeds the pool, so a concurrency of 1 cannot
deadlock. Two kinds of render count as heavy: named `full`, and an arbitrary box larger than
2048 px on either axis, or one with an unset dimension. All other renders weigh 1. At the default
concurrency of 2, one heavy render excludes all other work. Hosts with limited RAM and 60 MP
sensors keep the concurrency at 2 or 1.

Every render runs with a deferred slot release and a `recover()`. A crafted header on this
authenticated path can therefore never leak a slot.

### 1.6 Frontend, and the clipboard constraint

- `frameImageUrl(frame, size)` builds the content-stamped URL. `frameHasImage(frame)` mirrors the
  backend's eligibility exactly (state, `dest_path`, `sha256`), so an ineligible row renders a
  placeholder and makes no request. `FrameThumb` renders a lazy `<img>`, falls back to the
  placeholder on error, and opens the lightbox on click. Thumbnails appear in History, the
  Devices card's Recent transfers and Unclassified lists, and the Feed. The frame detail modal
  shows an inline `card`.
- `FrameLightbox` wraps `yet-another-react-lightbox` with its Zoom and Download plugins. The slide
  opens on `screen`. Its `srcSet` lists `full` at the native dimensions from `/image/meta`, so
  zooming in loads the native render: pixel-level focus and star inspection without paying for
  the native render on open. Download fetches `full`.
- **Copy** writes `image/png`, the only type browsers reliably accept, through a canvas. The
  `ClipboardItem` is built **synchronously in the click handler** with a promise value, because
  Safari and others drop the user activation across `await`s. It tries `full` first and falls
  back to `screen` when the native image is too large to fetch or encode. The Clipboard API
  requires a secure context, so the button appears only when `window.isSecureContext` holds and
  `navigator.clipboard.write` exists. The HTTPS listener ([architecture
  §8.5](2026-10-17-architecture.md)) normally provides one; it is best-effort, and if it fails to
  bind, the server serves plain HTTP only. On the plain-HTTP port, other than from
  `localhost`, Copy is hidden and Download still works.

Configuration (all three apply on restart, because the `Previewer` is built from a config snapshot
at startup; see [architecture §3.8](2026-10-17-architecture.md)):

| Key | Default | Meaning |
|---|---|---|
| `previews_enabled` | `true` | Master switch. When false, a nil `Previewer` is injected: the warm is a no-op and the endpoints return 503. |
| `preview_concurrency` | `2` | Size of the semaphore; must be ≥ 1. |
| `preview_cache_max_bytes` | 2 GiB | LRU cap; must be ≥ 256 MiB, so the cap always holds a `full` entry. |

JPEG quality and the named dimensions are constants, not configuration. Config schema v2 is the
migration that seeds the three keys for configs written before they existed, so an upgraded
install loads with previews enabled ([architecture §7.3](2026-10-17-architecture.md)). The
migration is load-bearing because `config.Load` does not run `Validate`: without it, an upgraded
config would load at the Go zero values, with previews off and `preview_concurrency` 0, and
nothing would reject it. `Defaults()` passes `Validate` with no errors
(`TestDefaultsValidateClean`), so the seeded values are always valid ones.

### 1.7 Rejected alternatives

| Alternative | Why it was rejected |
|---|---|
| Reuse the ASIAIR's own `_thn.jpg` previews | The pull excludes `jpg`/`jpeg` by default as sidecars, so those bytes never reach the archive. |
| Render every size at filing time | A night produces thousands of frames and most are never opened. Only the size every list needs is warmed. |
| Fully lazy, nothing warmed | The first view of a list of recent frames would render every visible row at once. |
| Cache arbitrary `w`/`h` sizes | Unbounded cache cardinality. Arbitrary sizes are served uncached, bounded by the semaphore and the pixel ceiling. |
| Bilinear demosaic for every size | It needs a full-resolution three-channel buffer (about 300 MB for a 26 MP sensor) even for a 256 px thumbnail. Superpixel is faster, free of artefacts, and its half resolution is irrelevant at preview sizes. |
| Mono-only rendering | One-shot-colour cameras are common on ASIAIR rigs, and would render as a grey mosaic. |
| A hand-rolled FITS sample reader | `fitsio`'s `Read` is proven across every `BITPIX`/`BSCALE`/sign case. Re-deriving it trades that proof for a small dependency saving. `internal/header` keeps the cheap pre-allocation gate. |
| A lightbox built on the in-house `Dialog` | Zoom, pan, touch handling, focus trapping and keyboard navigation are fiddly. The library is small, maintained and compatible with React 19. |
| A configurable NAS cache root | Previews are derived and rebuildable, not archival, so they live under the data directory with an LRU cap and need no operator configuration. |

## 2. Frame astrometry from the embedded WCS

The ASIAIR plate-solves on the mount and writes a World Coordinate System solution into the light
frames it solved: where the telescope pointed, the image scale and the field rotation. **Tier 0**
reads what is already in the header. It stores it per frame, backfills existing frames once, and
shows the coordinates and rotation in the frame lists. A framing failure that is otherwise
invisible until processing therefore shows at a glance. A camera assembly that rotates part-way
through a session, for example, appears as a rotation column that changes mid-run. Tier 0 does no
solving of its own. Tier 1 (§3) plugs into the same columns.

Out of scope: alerting on drift (a human reads the numbers), and exact per-pixel sky mapping (SIP
distortion is ignored, because it does not affect the centre, scale or rotation).

### 2.1 The extractor

`astrometry.FromHeader(h model.Header) *model.Astrometry` is pure. It does no I/O and never panics
on odd values, the same contract as `classify.Classify`. It is deliberately a separate package
from classification: classification is about routing and stays minimal, while astrometry has its
own lifecycle and its own second producer (Tier 1).

**Solution.** A solution exists only for a tangent-plane WCS in RA-first order: `CTYPE1` starts
with `RA---` and `CTYPE2` starts with `DEC--`. A swapped order is treated as no solution, not
silently transposed. The linear transform is the `CD` matrix when any `CDi_j` card is present
(absent elements default to 0). Otherwise `CDELT1/2` and `CROTA2` (default 0) are synthesised into
a CD matrix. A determinant with `|det| < 1e-30` means no solution, which also prevents an
`atan2(0,0)` from reporting a bogus 0° rotation. From a valid CD matrix, `CRVAL` and `CRPIX`, the
extractor derives:

- **Centre RA/Dec** (degrees): the sky position of the image centre `((NAXIS1+1)/2, (NAXIS2+1)/2)`.
  It is computed as `(ξ,η) = CD·(centre − CRPIX)`, then the division-free AIPS TAN inverse about
  `(α0,δ0) = CRVAL`, with `X,Y = (ξ,η)` in radians:
  `α = α0 + atan2(X, cosδ0 − Y·sinδ0)`, `δ = atan2(sinδ0 + Y·cosδ0, √((cosδ0 − Y·sinδ0)² + X²))`.
  This form returns `CRVAL` cleanly, with no `0/0`, when `CRPIX` is centred, as the ASIAIR writes
  it. A header that anchors `CRPIX` off centre (a mosaic tile, a reference star) still yields the
  true centre.
- **Position angle**, in [0,180): parity-aware, in astrometry.net's orientation convention
  (`tan_get_orientation`), then folded by 180°. With `det = CD1_1·CD2_2 − CD1_2·CD2_1`:

  ```
  parity = det ≥ 0 ? +1 : −1
  T      = parity·CD1_1 + CD2_2
  A      = parity·CD2_1 − CD1_2
  pa     = fold180(−atan2(A, T))
  ```

  A rectangular sensor's footprint is unchanged by a 180° rotation, and stacking
  software derotates, so a meridian flip or a camera reinserted end-for-end reads as about 0°
  change instead of a spurious 180°. What remains is genuine framing drift. The value is a raw
  per-frame number with no target-relative baseline.
- **Mirror flip:** `det(CD) > 0`. The normal sky view has a negative determinant.
- **Pixel scale:** `3600·√|det(CD)|` arcsec/px.
- **Field of view:** `NAXIS1·scale/3600` × `NAXIS2·scale/3600` degrees, or 0 when the `NAXIS`
  cards are absent.

The WCS math follows FITS WCS Paper II (Calabretta & Greisen 2002) and wcstools `getrot`.

**Hints.** Hints are read whenever the cards are present, independently of any solution. They are
the seed Tier 1 needs:

- Object RA/Dec: numeric `RA`/`DEC` in degrees (the ASIAIR's convention). Without those, the
  extractor falls back to the `OBJCTRA` (hours, ×15) and `OBJCTDEC` sexagesimal strings, split on
  whitespace or colons.
- `FOCALLEN` (mm) and `XPIXSZ` (µm per binned pixel: the ASIAIR writes it "with binning", see
  [asiair-hardware-notes §8.1](2026-10-17-asiair-hardware-notes.md)).

Each hint is a pointer, so an absent card differs from a real 0.

**Status.** `header` when a solution was produced, otherwise `none`. `none` means "no embedded
solution": every calibration frame, and every light the mount did not solve. It does not mean
"unsolvable". Which lights carry a WCS is the device's behaviour (see
[asiair-hardware-notes §8](2026-10-17-asiair-hardware-notes.md) and H13).

Tests: `TestFullCDSolution`, `TestCDELTMatchesCD` (a CD matrix and its CDELT/CROTA2 equivalent
give the same angle, guarding the classic 180° or dropped-sign disagreement),
`TestPositionAngle180Fold`, `TestMirrorFlipped`, `TestOffCenterCRPIX`, `TestDegenerateCD`,
`TestSwappedAxes`, `TestHintsSexagesimal`, `TestHintsNumeric`, `TestCalibrationNoWCSWithHints`,
`TestBiasNeither`.

### 2.2 wcs_status: the lifecycle discriminator

One free-text `TEXT` column encodes the whole astrometry lifecycle and is the indexable key for
both work queues:

| `wcs_status` | Meaning | Set by |
|---|---|---|
| `NULL` | not yet processed | (Tier 0 backfill queue) |
| `header` | embedded WCS extracted; terminal | Tier 0 |
| `none` | no embedded WCS | Tier 0; the Tier 1 queue is the `LIGHT` subset |
| `solving` | claimed by the solve worker; transient | Tier 1 (§3.1) |
| `solved` | solved by Tier 1; terminal | Tier 1 |
| `failed` | the solver ran and found no match; terminal | Tier 1 |
| `unsolvable` | refused before solving; terminal, with one exception | Tier 1 |

Because the column is free text, the Tier-1 values need no schema change. Per-attempt detail
(reason, solved-at, attempts, field size) rides in the JSON blob. `frame_type` is stored upper-case
(`model.TypeLight = "LIGHT"`) and SQLite string comparison is case-sensitive, which the queue
queries respect.

### 2.3 Persistence and write discipline

The `frames` row carries `wcs_status` and `astrometry` (the JSON of `model.Astrometry`: status,
solution, hints, and the Tier-1 fields). This follows the `sidecars` JSON precedent rather than a
dozen flat columns. `model.Frame.Astrometry` gives a clean tri-state: nil means unprocessed;
`Solution == nil` means processed with no WCS; a non-nil `Solution` means a solution exists. The
column duplicates the blob's status only so the queues can be indexed without `json_extract`.
Both always move together (§3.9 invariant 2). Two partial indexes serve the two queues:
`idx_frames_need_astro` (`WHERE wcs_status IS NULL`) and `idx_frames_need_solve`
(`WHERE wcs_status='none'`).

**A re-pull never erases a solution.** Only these paths write the two columns:

- the ingest `INSERT`: a freshly filed frame carries its header astrometry immediately;
- the targeted writers: `SetFrameAstrometry` (unconditional), `SetFrameAstrometryIfPending`
  (`WHERE wcs_status IS NULL`, for the backfill) and the Tier-1 writers of §3.5;
- `ClearFrameAstrometry`, the deliberate reset.

`UpsertFrame`'s conflict clause preserves the stored values. For a `NULL`, `none` or `header` row
it applies `COALESCE(excluded, existing)`, so a write that carries no astrometry (`markFailed`, a
reclassify move) never nulls a value. For a Tier-1 status it keeps the stored value outright
(§3.5.1). `UpdateFrame`, used by the delete lifecycle, does not name the columns at all. The
outcome does not depend on insert order. Guards: `TestUpsertNilAstrometryPreservesSolution`,
`TestAstrometryRoundTrip`, `TestAstrometryNilStoresNull`.

The store's schema version (`model.CurrentStoreSchemaVersion`) is separate from the config schema
version, so a store-only migration never forces a config migration ([architecture
§7.8](2026-10-17-architecture.md)).

The API's `frameDTO` carries `astrometry` straight from `model.Frame`; its types already have
snake_case tags. Every frame event goes through the same DTO (§4.4), so a freshly filed frame
streams its coordinates with no extra wiring.

### 2.4 Backfill

`rig.BackfillAstrometry` runs once in the background at startup and walks frames with an
**advancing id cursor**:
`ListFramesNeedingAstrometry(afterID, 256)` → `WHERE id > ? AND wcs_status IS NULL AND
dest_path <> '' AND state IN ('verified','deleted','unclassified','held') ORDER BY id`. This is
the same set of copy-retaining states the image endpoint uses. `deleted` is included on purpose,
because its `dest_path` is the permanent archive.

The cursor advances past **every** attempted row, whatever the outcome, and the loop ends on a
short page. The cursor is load-bearing: an unreachable file is deliberately left `NULL`, so a loop
that ran until a batch came back empty would re-fetch the same rows forever in a hot `os.Stat`
loop. Rows left `NULL` are retried at the next startup.

Failure is classified by **reachability, not by error string**:

- A failed `os.Stat` of `dest_path`, of any kind (`ENOENT`, a share that is not ready, a stale
  mount), is transient. Nothing is written.
- A `ReadHeader` failure on a file that did stat (truncated, not FITS, no `END` card) is
  deterministic and writes `none`. The residual is a NAS that drops between the stat and the
  read.

The check is deliberately broader than `fs.ErrNotExist`. A briefly offline NAS raises other
errors, and `none` is never re-queued by Tier 0, so a misclassification would never self-heal.

Writes go through `SetFrameAstrometryIfPending`, so a live re-pull that populated the row first is
never clobbered. The pass is single-threaded with a 3 ms pause between reads, so its `dest_path`
reads cannot starve live pulls on the same storage. It logs a progress line every 500 frames.
When it writes `none` on a `LIGHT`, it nudges the solve worker (§3.6). Ordering relative to the
workers does not matter, because the data is display-only. Guard: `TestBackfillAstrometry`.

### 2.5 Interpreting rotation

The History and Recent transfers tables show **Coordinates** (`HHhMMmSSs ±DD°MM′SS″`, with
60-second carries rolled into the next unit) and **Rotation** (the position angle, with a flip
indicator). The detail modal shows the full breakdown: centre, rotation, scale, field of view,
flip, the hints, and a status label ("from header", "no solution", "pending" while the row is
still `NULL`, or the Tier-1 labels of §3.8), so every state reads distinctly. Because the angle is
folded to [0,180), a value that changes between frames of one run is real framing movement. Turning
"differs from the run's established angle" into an alert would be a separate feature.

### 2.6 Rejected alternatives

| Alternative | Why it was rejected |
|---|---|
| Write a solver before reading the header | The WCS the ASIAIR already wrote shows the motivating failure with no solving. Solving is a large effort dominated by distributing star catalogues; it is Tier 1, behind this seam. |
| About a dozen flat columns | Every field would churn the four lockstep sites (`frameColumns`, `scanFrame`, `UpsertFrame`, `UpdateFrame`) and need a migration. Nothing sorts or filters on these fields server-side. |
| A 0-sentinel mapped to NULL, as for `Night` | RA 0°, Dec 0° and rotation 0° are legitimate values. Presence is structural (nil pointers). |
| Report `CRVAL` as the centre | That is correct only when `CRPIX` is centred; otherwise the error is degrees. One linear and gnomonic step is cheap. |
| One schema-version constant shared by config and store | A store-only migration would force an unregistered config migration and break config loading. |
| Backfill by walking the filesystem | The database already indexes every frame with its `dest_path` and state, and `wcs_status IS NULL` is a natural, resumable queue. |
| Extract inside `classify.Classify` | It mixes a routing concern with a separate lifecycle that has a second producer. |

## 3. Plate solving

The mount solves only periodically, so many ordinary lights carry no WCS. With Tier 0 alone, a
night can show mostly blank coordinates. **Tier 1** solves those lights in the background with
ASTAP's command-line solver. It streams each result into the UI as it lands, without slowing
ingest or blocking the interface. The output is the same `model.WCSSolution` Tier 0 produces.

The design rests on one structural fact: **the solver's output is itself a FITS header.**
`astap_cli -wcs` writes a data-less FITS (`.wcs`) that merges the original cards with the solved
`CTYPE`, `CRVAL`, `CRPIX` and `CD` cards. Feeding it back through `internal/header` and
`astrometry.FromHeader` yields the Tier-0 shape. Tier 1 is therefore a second producer of the same
shape, with no astrometry math or persistence of its own.

Out of scope: blind solving (a policy, §3.11); solving calibration frames, which are never queued;
automatic drift alerting; re-solving `header` or `solved` frames.

### 3.1 The lifecycle

| `wcs_status` | Set by | UI |
|---|---|---|
| `none` (a light) | Tier 0 | blank, queued |
| `solving` | the worker claims the row | "solving…" with a spinner |
| `solved` | the worker, on `PLTSOLVD=T` | coordinates and rotation |
| `failed` | the worker: the solver ran with no match, or the per-frame fault budget ran out | "solve failed" (reason in the title) |
| `unsolvable` | the worker, before solving | "cannot solve" (reason in the title) |

`unsolvable` has three causes: no pointing hint; a field of view that cannot be computed (missing
`FOCALLEN`, `XPIXSZ` or `NAXIS2`); or a field smaller than every installed catalogue's floor.

`failed` and `unsolvable` are terminal for the automatic machinery, with two ways back:

- **Below-floor re-queue (automatic).** An `unsolvable` frame refused for its field size records
  that size (`fov_deg`). When a deeper catalogue is installed, `RequeueFloorUnsolvable(floor)`
  flips every such frame whose `fov_deg ≥ floor` to `none`. "Download a deeper catalogue" is
  therefore actionable advice, not inert text. Startup repeats the call with the deepest installed
  floor as a safety net.
- **Re-solve failed frames (manual).** A Settings action, `POST /api/platesolve/resolve`
  (`RequeueSolveFailures`), returns every `failed` row to `none` with its attempt count reset. A
  marginal frame that a shallow catalogue nominally covers but is too sparse to match lands in
  `failed`, not in below-floor `unsolvable`, so this is how it gets another try under a deeper
  catalogue.

A no-hint `unsolvable` stays put, because re-solving cannot help it.

Both re-queues write `'none'`, not `NULL`. `NULL` is the Tier-0 queue, which runs only at startup;
`'none'` is what the re-sweep, the nudge and `ClaimFrameForSolve` target, so the frames re-solve
without a restart. `solving` is reclaimed to `none` at startup (`ReclaimSolvingFrames`), so a crash
mid-solve heals itself.

### 3.2 What a hint buys

The pixel scale is not merely hinted; it is **known**:
`scale = 206.265 · XPIXSZ / FOCALLEN` arcsec/px. The field height follows as
`scale · NAXIS2 / 3600`. Binning is already in both factors: `XPIXSZ` is the binned pixel pitch
(§2.1) and `NAXIS2` counts binned rows, so a bin-2 frame has the same field as its bin-1 twin.
Multiplying by `frames.binning` as well would double the hinted field of every binned frame.
Guard: `TestSolveOne_BinnedFrameFOVMatchesUnbinned`. With an approximate centre from the object RA/Dec card, which sits within
a few degrees of the true centre in practice, the solve collapses from searching the sky to
confirming and refining a known position. A hinted solve of a field several degrees wide completes
in well under a second with a 10° search radius. A frame with no position card has a scale but no
position, and that is the case Tier 1 refuses.

### 3.3 Invoking ASTAP, and reading its result

```
astap_cli -f <frame> -ra <RA_deg/15> -spd <Dec_deg+90> -fov <field_height_deg> \
          -r <radius_deg> -z 0 -d <catalog_dir> -wcs -o <work>/<per-solve dir>/<base>
```

- `-ra` is in **hours**; `-spd` is the **south-polar distance**, Dec + 90, in degrees; `-fov` is
  the field **height** in degrees. Commander passes the computed `-fov` rather than `0`
  (auto-detect): auto-detect scans several candidate scales, which is slower and less
  deterministic, and the field size is needed anyway for catalogue selection.
- `-o` points into a per-solve directory under `<data-dir>/astap/work/`, which `RemoveAll`
  deletes on return, deadline included. Nothing is ever written beside the source frame on the
  NAS, and a leftover from a crashed solve can never be read as another frame's result.
- **Success is `PLTSOLVD=T` in the `.ini`, never the exit code.** `astap_cli` exits 0 when it finds
  no solution. Reading the exit code is the natural first assumption, and it would silently mark
  every failed solve as solved. `PLTSOLVD=F` is a clean "no star match".
- **The `.wcs` carries `NAXIS=0` and no `NAXIS1`/`NAXIS2`**, so `FromHeader` would report a field
  of view of 0. `model.Header` has no mutator, so the adapter rebuilds the card slice and appends
  the source frame's `NAXIS1`/`NAXIS2` **last**. `NewHeader` lets a later duplicate win, so the
  appended cards override a `.wcs` that carries `NAXIS1=0`. Centre, rotation, scale and flip are
  unaffected: ASTAP writes `CRPIX` at the image centre, with `CRVAL` there.
- `PLTSOLVD=T` with a missing or unparseable `.wcs` is a clean `failed` ("solved but .wcs
  unreadable"), not an operational error. As an operational error it would retry forever.
- Operational errors cover infrastructure faults: a missing binary or catalogue, an unreadable
  `.ini`, or an `.ini` with no `PLTSOLVD` line. A solve that exceeds its 120 s deadline returns
  `ErrSolveTimeout`. Arguments go through `exec.Command` as argv with no shell, so file names
  with spaces need no quoting.

Guards: `TestParsePLTSOLVD`, `TestWithNAXISOverlay`.

### 3.4 The solver package, provisioner and catalogs

`internal/platesolve` holds the `Solver` interface, its real implementation (`astap.go`), and a
`FakeSolver` that returns scripted results by path, so no test needs a binary or a network. A nil
error with `Solution == nil` is a clean miss. A non-nil error is operational.

**Binary resolution.** The binary is looked up beside the service executable (the bundled copy),
then on `PATH`. There is no runtime binary download, because no reliable upstream single-binary
URL exists; the binary is delivered by bundling (§3.10). With no binary found, the provisioner
publishes `failed` ("astap_cli not found") and solving stays paused.

**Catalogs.** Which catalogues are installed is **disk state**, not configuration: the presence of
`.1476` tiles under `<data-dir>/astap/<name>/`. Catalogues are downloaded, never bundled. The pins,
ordered from shallow to deep, are:

| Catalog | Zip size | Solves fields | Role |
|---|---|---|---|
| `d05` | ~102 MB | ≳ 0.6° | downloaded automatically on first run (the wide-field default) |
| `d20` | ~400 MB | ≳ 0.3° | on demand, from Settings |
| `d50` | ~900 MB | ≳ 0.2° | on demand, from Settings |

Each pin is a stable upstream URL with a size and SHA-256 computed once. The upstream catalogues
are static. A deeper `d80` is not offered: it has no resolvable upstream URL, and `d50`'s floor
already covers realistic long-focal-length fields.

- `CatalogFor(fov)` returns the **shallowest installed** catalogue whose floor is ≤ the field
  (shallower is faster, and any covering catalogue is correct).
- When none covers the field, the frame is `unsolvable`, with a reason that names the smallest
  catalogue that would (`SmallestCovering`).
- `Ready()` is true when the binary is resolved and at least one catalogue is installed, so `d05`
  alone is enough to start.

**Downloads** run under the app context captured by `Start`, never under a request context:

- **Resumable.** The zip streams to `<name>.part` with `Range: bytes=N-`, and the response status
  decides what happens: 206 appends, 200 truncates and restarts, 416 means the file is complete.
- **Integrity-checked.** The completed file is checked against the pinned size and SHA-256. Any
  mismatch deletes the `.part`, whether it was fresh or resumed, because a retained corrupt
  partial would fail forever.
- **Installed atomically.** The zip unzips into `<name>.tmp/`, which is renamed to `<name>/`, so a
  crash mid-unzip can never leave a partial catalogue that `CatalogFor` would trust.
- **Space-checked.** A free-space precheck on the data volume, which is not the destination volume
  `disk_reserve_bytes` protects, reserves about twice the zip size, because the zip and its
  unzipped tree coexist at the peak.
- **Visible.** Progress publishes at most about once per 1% or 500 ms.
- **Unbounded in time.** The HTTP client sets no overall timeout, because the catalogues are
  large. A download ends when it completes, fails, or the app context is cancelled at shutdown,
  so a stalled body read holds the solve/download gate (§3.9 invariant 6), and pauses solving,
  until then.

The first-run download of `d05` retries with a linear backoff (30 s × attempt, capped at 10
minutes). After 3 consecutive failures it raises a warning alert (category `config`), so a stuck
download shows instead of leaving solving silently paused. A completed download re-queues the
below-floor frames it covers and wakes the worker.

**Observable state, push-only.** `model.ProvisionStatus` has a state (`disabled`, `provisioning`,
`ready` or `failed`), a detail, every catalogue with its installed flag and pinned size, and the
in-flight download's progress. It rides the status snapshot as `solver_status`
(`hub.SetSolverStatus`), so there is no read endpoint.

### 3.5 Store guards

Three guards make the two writers, the ingest worker and the solve worker, safe against each
other.

#### 3.5.1 Tier-1 states are sticky

On conflict, `UpsertFrame` keeps the stored `wcs_status` and blob whenever the row holds `solving`,
`solved`, `failed` or `unsolvable`. For `NULL`, `none` or `header` it applies the Tier-0 `COALESCE`
(§2.3):

```sql
wcs_status = CASE WHEN frames.wcs_status IN ('solving','solved','failed','unsolvable')
                  THEN frames.wcs_status
                  ELSE COALESCE(excluded.wcs_status, frames.wcs_status) END
-- astrometry: the same CASE on the same condition
```

A plain `COALESCE` is not enough. A re-file of a light with no embedded WCS carries a **non-nil**
`Status="none"` from `FromHeader`, so `COALESCE` would pick it, erase a solution, and re-queue a
frame that is never supposed to re-queue. The clobber reverts `wcs_status` and the blob together,
so it never desyncs them (invariant 2 in §3.9 still holds); the damage is lost data, which is why
stickiness is its own invariant. Guard: `TestUpsertStickyGuard`.

Stickiness has one sanctioned exception: a content change, which must clear the row explicitly
with `ClearFrameAstrometry` (`NULL`/`NULL`) so the changed bytes are re-extracted and re-solved. The
supersede path is that caller ([frame-lifecycle §11.10](2026-10-17-frame-lifecycle.md)). It clears,
then records the revised file's own Tier-0 extraction. Guard: `TestClearFrameAstrometry`.

**Known gaps.**

- A differ re-pull ([frame-lifecycle §4.2](2026-10-17-frame-lifecycle.md)) puts genuinely
  different content at the same path, and it reaches `UpsertFrame` with no clear. A row that held
  a Tier-1 verdict keeps it across the re-pull, so `solved` coordinates can describe the previous
  exposure at that path.
- A restore that installs revised bytes leaves a pre-revision verdict standing (frame-lifecycle
  §11.10 records that residual).

Both are display-only: astrometry never feeds a delete or routing decision.

#### 3.5.2 Upserts report the effective state

`UpsertFrame` uses `RETURNING id, wcs_status, astrometry` and writes the **persisted** values back
onto the caller's frame before `recordFiled` emits `frame.done`. A re-file of a solved row
therefore reports `solved`, not the incoming `none`, and the solve-enqueue check reads the
effective status. `RETURNING` must include `id`: `QueryRow` has no `LastInsertId`, and a fresh
insert would otherwise leave `f.ID == 0` and break the solve nudge. Guard:
`TestUpsertReturnsInsertID`.

#### 3.5.3 The terminal write is a guarded compare-and-set

The worker's claim, solve (up to 120 s) and terminal write hold no lock across the subprocess. The
single write connection serialises statements, not that sequence. Every write after the claim
therefore goes through `SetFrameSolveResult`
(`UPDATE … WHERE id=? AND wcs_status='solving'`, returning whether one row changed). The claim
itself is `ClaimFrameForSolve` (`WHERE wcs_status='none'`). The blob it writes carries
`Status="solving"` and keeps the hints, so column and blob move together.

If the row left `solving` during the solve (for example, a supersede cleared it), the compare-and-set
misses. The worker then **discards the result and emits nothing**, because the racing writer's own
effective emit (§3.5.2) already carries the truth. Otherwise a WCS computed from bytes that no
longer exist would land on the row. The unconditional `SetFrameAstrometry` is never used for
Tier-1 terminal writes, and `SetFrameAstrometryIfPending` guards `IS NULL`, which is the wrong
condition for these rows. Guards: `TestClaimFrameForSolve`, `TestSetFrameSolveResultGuarded`,
`TestSolveOne_MidSolveResetDiscards`.

The store's JSON1 uses (`json_set` in the reclaim and re-queues, `json_extract` on `fov_deg`) rely
on the JSON1 extension bundled in `modernc.org/sqlite`. `TestReclaimSolvingFrames`,
`TestRequeueFloorUnsolvable` and `TestRequeueSolveFailures` exercise them.

### 3.6 The solve worker

`rig.RunSolver` is one long-lived goroutine, started only when `plate_solve_enabled` is set. It
takes the provisioner through the three-method `platesolve.SolveGate` seam (`Ready`, `CatalogFor`,
`BeginSolve`), so tests fake it.

- **Gate.** The worker waits for `Ready()`, polling every 2 s and draining nudges meanwhile. Until
  a catalogue lands, nothing is claimed, and lights stay `none` and blank.
- **Backlog drain.** The worker walks `ListFramesNeedingSolve` (the `none` `LIGHT` rows in the
  copy-retaining states, `dest_path` set) by an advancing cursor in pages of 256, with a 3 ms
  pause between solves. This is the backfill's termination logic. A from-zero **re-sweep every 5
  minutes** catches rows Tier 0 flipped to `none` behind the cursor.
- **Live path.** A buffered channel (256) of frame ids is read alongside the re-sweep tick.
  `recordFiled` sends on it (§3.7), and so does the Tier-0 backfill when it marks a light `none`.
  Sends are non-blocking. **The database is the queue of record**, so a dropped nudge is picked up
  by the next sweep. On first run, the backfill usually finishes before the catalogue download, so
  its nudges are dropped while the worker waits on `Ready()`. That is harmless; the nudge's
  latency gain matters in steady state.
- **Yield to downloads.** Before each frame the drain checks `DownloadPending()` and stops when a
  catalogue download is queued or running. The download then gets the gate after the current solve
  instead of after the whole backlog, and wakes the worker when it finishes.

**`solveOne(f)`**, under a per-frame `recover()`, runs these steps:

1. `BeginSolve(ctx)` acquires the solve/download gate. It is context-aware, so shutdown is never
   stuck behind a multi-minute download.
2. `os.Stat(dest_path)`. An unreachable file is transient: leave the row `none`.
3. Re-read the source header for `NAXIS1/2` and fresh hints. This hardens the list→claim window. A
   read failure after a good stat is transient.
4. **Disposition:** no RA/Dec hint, no computable field, or a field below every installed floor
   makes the frame unsolvable, with a reason and `fov_deg`. Otherwise the frame is solvable, with
   the chosen catalogue directory.
5. `ClaimFrameForSolve` moves the row from `none` to `solving`. A missed claim (the row was
   re-pulled, solved or claimed already) means nothing is owed.
6. **Unsolvable:** write `unsolvable` through the compare-and-set with no "solving…" emit (so the
   row never flickers), emit, and log at Info.
7. **Solvable:** emit `frame.done` carrying `solving`, then solve with the live
   `plate_solve_radius_deg`:
   - `Solution != nil`: write `solved` with `solved_at`.
   - Clean miss: write `failed` with the reason. A wildly wrong hint that puts the true centre
     outside the radius is a clean miss too, which is why `plate_solve_radius_deg` matters, and
     why "Re-solve failed frames" under a deeper catalogue may not help such a frame.
   - Operational error: an **unbudgeted** transient. Reclaim to `none` with no attempt counted, and
     clear the spinner. Budgeting it would stamp the whole backlog `failed` within a few sweeps
     when, say, antivirus quarantines the binary; that failure belongs to provisioning.
   - Timeout or panic: a **per-frame** fault. Increment `attempts` in the blob. At 3 attempts
     (`maxSolveAttempts`) the frame becomes terminal `failed` ("repeated solve timeout" or
     "repeated solver error"); below that it returns to `none`. A poison frame terminalises instead
     of livelocking the re-sweep or monopolising the gate.
8. Emit `frame.done` only after a compare-and-set that succeeded. The UI merges `frame.done` by id.

The frame read is the filed `dest_path` copy, which was verified and atomically renamed before
filing, so a partial read is precluded by construction. One worker plus the inter-solve pause keeps
the full-frame read from starving live pulls.

Guards: `TestSolveOne_Solved`, `TestSolveOne_NoMatchFailed`, `TestSolveOne_NoHintUnsolvable`,
`TestSolveOne_MissingFileTransient`, `TestSolveOne_BelowFloorUnsolvable`,
`TestSolveOne_MidSolveResetDiscards`, `TestSolveOne_PoisonFrameBudget`,
`TestSolveOne_TimeoutBudget`, `TestDrainYieldsToDownload`, `TestListFramesNeedingSolve`.

### 3.7 The ingest hook

After a successful `UpsertFrame` and its emit, `recordFiled` calls `maybeEnqueueSolve(f)`. That
helper sends `f.ID` on the nudge channel when the frame is a `LIGHT` whose **effective**
`Astrometry.Status` is `none`. Because §3.5.2 writes the effective status back, a re-file of a
solved frame reports `solved` and is not enqueued: the sticky guard and the effective read close
the loop together. One call site covers both `classifyAndFile` and `reclassifyOne`, since both
funnel through `recordFiled`. The supersede path calls it as well, because a revised light may
still carry no WCS. `markFailed` is untouched.

### 3.8 Wiring, configuration and UI

At startup, when plate solving is enabled, `main.go` creates the nudge channel and the
provisioner, and calls `Start`. It reclaims `solving` rows, runs the below-floor re-queue for the
deepest installed floor, and launches `RunSolver`. `BackfillAstrometry` runs at startup whatever
the setting (§2.4), and receives the nudge channel, which is nil when plate solving is off. The
channel reaches `recordFiled` through `manager.New` and `rig.NewWorker`. The provisioner sits on
`web.Deps` as an optional dependency: nil-guarded, with a 503 when absent.

| Key | Default | Applies | Meaning |
|---|---|---|---|
| `plate_solve_enabled` | `true` | on restart (the provisioner and worker start once) | Master switch. Off publishes `disabled` and starts no worker. |
| `plate_solve_radius_deg` | `10` | live (read per solve from the config pointer) | Hint search radius, validated to 1–60. |

Config schema v3 is the migration that seeds both keys for configs written before they existed.
Because the default is on, an upgraded install downloads `d05` in the background, visible in the
provisioning indicator. There is no binary-path setting.

**Routes**, both under `guardWrite`:

- `POST /api/platesolve/catalogs/{name}` returns 400 for an unknown name, 503 when the provisioner
  is nil, 200 when the catalogue is already installed, 409 when a download is in flight, and
  otherwise 202, starting the download under the app context. A small lock inside the provisioner,
  separate from the gate, dedups a double submit.
- `POST /api/platesolve/resolve` is the manual re-solve, and returns the count re-queued.

**UI.**

- `AstrometryCells` branches on `astrometry.status` before the no-solution dash: "solving…",
  "cannot solve" or "solve failed", each with the reason as its title. The cells need only the
  `astrometry` object; a calibration frame and an unclaimed light both stay a plain dash.
- The detail modal adds "solved" beside "from header".
- The Settings "Plate solving" section holds the enable toggle (marked as applying after restart),
  the radius, a row per catalogue (coverage, size, Installed or a resumable Download with live
  progress from `solver_status`), the provisioning state, and "Re-solve failed frames".
- The provisioning indicator is a line at the top of the Settings star-catalog section, shown
  whenever `solver_status.state` is neither `ready` nor `disabled`: "Downloading the <name> star
  catalog… N%" while provisioning, or "Star catalog unavailable — plate solving paused." (or the
  status `detail`) when `failed`. It is what makes "solving is held until a catalogue lands"
  visible.

### 3.9 Concurrency and correctness invariants

Five actors touch these rows: the ingest worker, the Tier-0 backfill, the solve worker, re-pulls
and supersedes, and catalogue downloads. They are safe because:

1. **Each write and its emit carry persisted state, and only a successful compare-and-set emits.**
   One write connection serialises statements, and each subscriber's queue is FIFO. `Emit` is not
   held under the write lock, though, so emit order usually but not always follows write order
   across goroutines. What protects state is that `UpsertFrame` emits the `RETURNING` effective
   state (§3.5.2) and the solve worker emits only after a successful compare-and-set (§3.5.3). The
   database is never corrupted and a frame is never solved twice. The only residual is a transient
   UI glimpse, such as a stale "solving…" over a reset row, which heals on the next event or
   refetch. It is narrow: it requires the solve worker to be preempted across the ingest worker's
   whole network pull. Guards: `TestSetFrameSolveResultGuarded`, `TestSolveOne_MidSolveResetDiscards`,
   `TestUpsertReturnsInsertID`.
2. **`wcs_status` always equals `astrometry.status`.** Every writer sets both from one value. The
   claim writes a `solving` blob; the reclaim and re-queues use `json_set` on the status key;
   `UpsertFrame`'s two `CASE`s move together; `astrometryCols` returns both nil or both set. Guards:
   `TestAstrometryRoundTrip`, `TestAstrometryNilStoresNull`, `TestReclaimSolvingFrames`.
3. **Tier-1 states are sticky against a Tier-0 re-extraction.** Only `ClearFrameAstrometry` on a
   supersede, the solve worker, the two re-queues, or the startup `ReclaimSolvingFrames`
   (`solving` → `none`) move a frame out of `solving`, `solved`, `failed` or `unsolvable`.
   Guard: `TestUpsertStickyGuard`.
4. **`solving` is always recoverable and never livelocks.** The startup reclaim heals a crash, and
   the per-frame `recover()` heals a panic. Per-frame faults are budgeted to terminal `failed`
   after 3 attempts, so a frame neither stalls in `solving` nor flaps between `none` and `solving`.
   Guards: `TestReclaimSolvingFrames`, `TestSolveOne_PoisonFrameBudget`,
   `TestSolveOne_TimeoutBudget`.
5. **The database is the queue of record.** Nudges are latency hints, and a lost nudge is recovered
   by the from-zero re-sweep. A permanently unreachable `none` frame is re-listed each sweep: a
   small, bounded, indexed cost that heals if the file returns. This holds by structure:
   non-blocking sends, and a re-sweep from id 0. Guard: `TestSolveOne_MissingFileTransient`.
6. **Solving and catalog downloads never overlap.** The gate is a channel semaphore of size 1, so
   `solveOne` and `DownloadCatalog` are mutually exclusive. A catalogue's directory swap and its
   post-download re-queue therefore always run with no solve in flight. Guards:
   `TestGateMutualExclusion`, `TestDownloadQueuedBeforeGate`, `TestDrainYieldsToDownload`.

### 3.10 Delivering the solver

`astap_cli` (MPL-2.0, so redistribution is permitted) is **bundled** beside the service binary in
both deliverables, and resolved there first (§3.4):

- **The pin.** `deploy/astap/astap-cli.json` is the single source of truth: the ASTAP CLI version
  and, per platform, the upstream file and the SHA-256 of its zip.
- **The fetch.** `tools/fetch-astap` downloads at build time, verifies the digest, and unpacks. The
  version-less upstream URL is overwritten in place whenever ASTAP releases, so the fetch falls
  back to the project's mirror of the pinned zips (one `astap-cli-<version>` prerelease per pin).
  That keeps any pinned commit byte-reproducible. A mirror prerelease is never deleted.
- **The container.** The image build fetches `linux/$TARGETARCH`. The pinned Linux binary is
  statically linked, so the runtime stage stays `distroless/static`. `BUNDLE_ASTAP=0` skips the
  fetch for offline builds, and solving then falls back to `PATH` or stays paused.
- **The installer.** It bundles `astap_cli.exe` when the payload contains it and deletes it on
  uninstall. Catalogues download into `%ProgramData%\ASIAIRCommander\astap`, where the service
  account holds Full `(OI)(CI)F` access, so it can write them. Uninstall offers to remove the
  catalogues, because they are fully reconstructible, unlike `config.yaml` and `state.db`, which
  it deliberately preserves.
- **Updates.** A weekly workflow re-pins the solver in a pull request held for manual review,
  because a solver change warrants a real end-to-end solve (`TestRealSolveE2E`, run by hand with
  a binary, a catalogue and a frame) before it ships.

CI runs no ASTAP; every test uses `FakeSolver`. Packaging detail is in [architecture
§19.3](2026-10-17-architecture.md) and `deploy/astap/README.md`.

### 3.11 Settled choices

1. **Hinted only.** A frame with no pointing hint is `unsolvable` ("no pointing hint; blind solving
   disabled"), with a log line. ASTAP can blind-solve, and such a frame still has a known scale.
   But an all-sky search is orders of magnitude slower, it is the case most prone to a false
   match, and frames that lack any pointing card are typically throwaway test shots. Blind solving
   would fit this structure as an opt-in setting.
2. **On by default.** `plate_solve_enabled` defaults to true, and `d05` downloads in the background
   on first run.
3. **`d05` automatic; deeper catalogues on demand.** Each catalogue gets a resumable download with
   live progress, and a below-floor frame re-solves automatically when a covering catalogue lands.
4. **The search radius is a setting** (`plate_solve_radius_deg`, default 10°).
5. **Downloads pause solving.** Downloads are user-initiated and infrequent. Pausing solving for
   one keeps every download step (resume, swap, re-queue) free of races.
6. **`solving` is persisted**, not held in memory. It gives the DTO and SSE path a real value to
   render, lets the claim `UPDATE` double as the concurrency guard, and lets a one-statement
   reclaim heal a crash. The cost, a transient value on disk, is nil.

### 3.12 Rejected alternatives

| Alternative | Why it was rejected |
|---|---|
| A self-written or pure-Go solver | Source extraction, catalogue matching and robust rejection are exactly where a young solver produces a confidently wrong WCS, and for a feature that exists to catch framing drift, a plausible wrong answer is worse than none. ASTAP is the solver KStars/Ekos, N.I.N.A. and CCDciel shell out to. Its cost, one external process, is contained behind `Solver`. |
| astrometry.net (`solve-field`) | It runs on Windows only through Cygwin or WSL, which rules it out for a Windows service, and its index files are large. ASTAP ships a native console binary for every target. |
| Read success from the exit code | Wrong: the exit code is 0 on a miss. |
| Let ASTAP auto-detect the field (`-fov 0`) | Slower and less deterministic, and the field is computed anyway for catalogue selection. |
| Bundle a star catalogue | Catalogues run from 100 MB to 900 MB; bundling one bloats every installer and image and pins a stale copy. |
| Download the binary at runtime | No reliable upstream single-binary URL exists, and the version-less one rolls. Bundling from a verified pin is reproducible. |
| A solve-jobs table, or flat queue columns | `wcs_status='none' AND frame_type='LIGHT'` is the queue (with a partial index), and per-solve detail rides in the blob, so nothing beyond the index needs a migration. |
| Hold `solving` in memory only | See §3.11 item 6. |
| Budget every solve error | A global fault (a quarantined binary, an unmounted catalogue volume) would mark the whole backlog `failed` within a few sweeps. |

## 4. Live transfer feed

Between "the device wrote the frame" and "the frame is filed", Commander needs one or more polls
to see the file, a quiescence wait, and the copy. Without a feed, the frame is invisible for that
whole span, which reads as "is this working?". An operator with several rigs also has no single
place to watch the fleet. The **Live feed** (`/feed`) is one page with one row per frame. A row is
born when Commander first sees the file, and it updates in place through **pending →
transferring → filed → deleted**, with a live progress bar during the copy. The Devices card's
**Recent transfers** panel uses the same engine, scoped to one rig.

The feed takes no part in discovery, quiescence, transfer, verification or deletion. It
reads state the worker holds in memory and the full-frame completion events.
Progress is not persisted; a frame still appears at most one poll interval after capture.

### 4.1 Decisions

1. **Pending frames are never persisted.** A `frames` row is created only at a terminal transfer
   outcome. Pending frames are an ephemeral list on the live status, merged client-side. The
   discovery and pull loop and every `frames` query are independent of it.
2. **One unified row per frame, keyed by `rig_id + source_share + source_path`.** The ephemeral
   pending row and the persisted row share that key, so the row simply updates, with no
   dedup step and no two-row flicker. The share is in the key because the settle layer keys on
   share and path, and one rig can expose several shares.
3. **Rows are ordered by the timestamp they display.** The **When** column renders
   `frameTime(frame)`: `pulled_at`, falling back to `mtime` (`web/src/util/frameTime.ts`). Rows
   still in flight have no such timestamp, so they hold the top of the list, newest discovery
   first. Every row with a persisted frame follows, sorted by `frameTime` descending. The sort is
   stable, so frames that share a second keep the order they entered the collection: the server's
   `id DESC` within a seeded page, arrival order for live rows. This makes "the When column never
   rises going down the list" true by construction. A completing row moves from the bottom of the
   live group to the top of the dated group, the adjacent position, so it never visibly jumps.
4. **Ghost pending rows are dropped silently ("d1"), only against an authoritative listing.** A
   file seen pending that vanishes before it ever transfers (a temporary or 0-byte file the device
   removes) has its row removed, with a short exit animation. It leaves no "skipped" tombstone,
   because that noise belongs to the unclassified and dismiss path. Removal runs **only** on a
   snapshot carrying `pending_listed === true` for that rig. It removes a row that is absent from
   the set and still pending, with no terminal event. Frames whose transfer is merely deferred stay
   in the set (§4.3), so they are never removed.
5. **Every pending frame is sent, with no cap.** In normal operation the set is tiny (at most
   about 20 rigs and about 40 pending frames in total). The one spike
   is a cold reconnect to a rig with a large untransferred backlog, which is accepted as a rare,
   transient cost on a LAN. A per-rig cap would bound it, but would bring back newest-first
   selection, a stable first-seen time, truncation detection, and a split d1 rule.
6. **The feed is its own page.** History remains the paginated, date-filterable
   forensic view.
7. **Feed rows are `<div>`s in a virtualised list** (`@tanstack/react-virtual`, which supports the
   dynamic row heights the bar and pill states need). 200 is the **server page size**, for the
   12-hour seed and each scroll-to-bottom `loadMore`; it is not an eviction threshold. Retained
   rows are capped separately at 2000 (`FEED_MAX_ROWS`), trimming the oldest rows overall, from the
   bottom of the tail first; only an extreme session would trim live head rows.
   Virtualisation bounds the DOM independently of that cap.

### 4.2 Row lifecycle

A row's display state is not "whatever input spoke last". The snapshot inputs (`pending`,
`current`) publish many times per cycle with partial or lagging data, so last-writer-wins would
flicker. Each row's state is the highest-priority condition true for its key:

| Priority | State | Condition | Renders as |
|---|---|---|---|
| 1–2 | terminal: `deleted`, or the final state | a `frame.deleted`, `frame.done` or `frame.failed` arrived for the key | a status pill (`verified`, `unclassified`, `held`, `failed`, `deleted`) |
| 3 | `transferring` | the key equals its rig's `RigStatus.current` | a live bar from `current.pct` and `bytes_per_sec` |
| 4 | `pending` | the key is in the rig's latest authoritative `pending` set | dimmed "Pending transfer", no bar |

The row stores only `terminalState`. Each render derives `terminalState ?? (isCurrent ?
"transferring" : "pending")`. A terminal state is **sticky against non-terminal inputs**, so a
snapshot whose `current` still names a just-finished file cannot regress the row. Between two
terminal events the last one wins: a re-adopted frame (a `deleted` source that reappears and is
re-pulled) moves from Deleted back to its final state instead of freezing.

**Transferring is derived from `current`, never latched by an event.** `current` is set for the
whole copy and cleared when it completes or aborts. `frame.started` is therefore not used by the
feed, so an aborted copy cannot strand a row in `transferring`. Only one frame transfers per rig at
a time.

**No abort strands or wrongly removes a row.** A transfer that ends without a terminal event,
deferred before it started or aborted transiently, leaves the frame in the next authoritative
pending set. The row stays dimmed through the retry backoff and shows the bar again when a retry
sets `current`.

A `verified → held` transition ([frame-lifecycle §9.2](2026-10-17-frame-lifecycle.md)) has no live
event. Held frames are rare, and the row picks up the change on the next seed refresh.

### 4.3 The pending set

`RigStatus.pending[]` is a list of `{source_share, source_path, size}`, and
`RigStatus.pending_listed` is the authority flag. `pending[]` is distinct from
`waiting_to_settle`, which stays the settling-only count behind the card's "still saving" line;
the feed does not use it, and the two are not merged. The rule is: **pending is every pull
candidate
that reached no terminal outcome this cycle.** A candidate that `decide` marks for pulling ends a
cycle filed (`frame.done`), hard-failed (`frame.failed`), or neither, and "neither" is what is
published. That one rule covers four cases without enumerating outcome codes:

- frames still settling ([frame-lifecycle §4.4](2026-10-17-frame-lifecycle.md));
- frames deferred before the copy (admission, disk reserve, a staging write fault);
- copies that started and aborted transiently;
- frames skipped because the mount was lost.

**Collection.** `transfer` returns `filed=false` for both a hard failure and a transient abort, so
the set cannot be keyed off its return value. The worker keeps two per-cycle collections instead,
on its own goroutine, with no lock:

- `cycleCandidates`, appended at **one** site, right after `decide` says pull and before the
  quiescence check;
- `terminalThisCycle`, keyed on `share + "\x00" + path` (the settle key), filled by the sites that
  emit a terminal outcome (`recordFiled`, `markFailed`, the supersede and no-file outcomes).

At the end of the listing, the published set is the candidates minus the terminal keys. Both
collections reset at the top of `pullPhase`.

**`pending_listed` is true on exactly one snapshot per cycle:** the end-of-listing snapshot of a
genuinely complete pass, `listingOK && ctx.Err() == nil && !workSuspended() && !destUnavailable`.
A per-share listing failure, a shutdown or pause break, or a destination-unavailable abort would
publish a partial set that the client would treat as complete, and d1 would remove real rows. The
flag is deliberately **not** gated on keep-originals, unlike the orphan sweep, or a keep-originals
rig would never reconcile. It resets to false at the top of every cycle, and the paused branch of
`publishListingStatus` clears it again, so mid-cycle and paused publishes never carry it. The
`pending` slice itself is left in place between authoritative snapshots; its staleness is
harmless, because the client ignores it unless `pending_listed` is true. An
`omitempty` slice cannot tell complete-and-empty from absent, which is why the flag exists: when
it is true, an empty set legitimately removes the last ghost.

Guards: `TestPendingListsSettlingFrame`, `TestPendingListsAdmissionDeferredFrame`,
`TestPendingExcludesFiledFrame`, `TestPendingExcludesHardFailedFrame`,
`TestPendingListedFalseOnPartialListing`, `TestPendingListedFalseWhenOffline`,
`TestPendingListedFalseWhenPaused`.

### 4.4 Completion events and the current file's identity

- **`frame.done` and `frame.failed` carry the full frame.** `Event.Data` is a `model.Frame` value.
  The SSE dispatch converts it with `toFrameDTO` (`frameEventData`), the same DTO the REST
  endpoints return, so the rig package never imports the web package. The conversion is a
  **checked** type assertion: the hub is untyped (`Data any`), and a mismatched payload must not
  panic the stream goroutine. A non-frame payload passes through unchanged. Guard:
  `TestFrameEventDataMatchesREST`.
- **`frame.deleted`** carries the same full-frame DTO through `frameEventData`, which is what the
  merge engine keys it by (§4.5). `markDeleted` emits it **only after** `UpdateFrame` persists
  `state='deleted'`, so the row never shows Deleted while the database still says verified.
  `holdFrame` emits nothing, because a held frame is kept, not deleted.
- **Late completions.** A Tier-1 solve, a re-file and a retarget all emit `frame.done` carrying the
  frame's original `pulled_at`, which is the grace anchor and is never restarted. That is why
  decision 3 orders rows by the displayed timestamp rather than by arrival.
- **`current` carries the full identity.** `CurrentFile` has `source_share` and `source_path` beside
  the basename `file`. Basenames collide (the same file listed on the Udisk and EMMC shares, H12),
  and a page opened mid-transfer has only `current` to build the key from. The progress path
  replaces `current` wholesale on each sample, to avoid racing the SSE marshal, so every rebuild
  copies the identity through (`Progressed`). Without that, the bar would revert to "Pending
  transfer" after the first sample.

### 4.5 The merge engine

`useFrameFeed({ rigId? })` (`web/src/surfaces/useFrameFeed.ts`) owns one keyed `Map` of rows. The
same implementation drives the fleet feed (no `rigId`) and the Devices panel (scoped).

- **Key.** `rig_id`, `source_share` and `source_path`, joined by NUL. The rig comes from the
  enclosing `RigStatus.id` for the snapshot inputs, and from `frame.rig_id` otherwise. An input
  missing `source_path` or `source_share` is skipped rather than given a garbage key.
- **Row.** `{key, rigId, share, path, size, zone, terminalState?, frame?, removing?}`. `zone` is
  `head` for a row first seen live, or `tail` for a row from the server. The `Map`'s insertion
  order is what zones, reseeding and trimming key off; render order is derived as decision 3
  describes.
- **Seed.**
  - Fleet: `GET /api/frames?from=<seed time − 12 h>&to=<seed time>&page_size=200` (`ListTransferHistory`,
    `pulled_at IS NOT NULL`, `id DESC`). Both window bounds are frozen at seed time and reused for
    every `loadMore`. Freezing only `from` would not stop the offsets from sliding, because frames
    filed during the session enter above the window.
  - Scoped: the rig's newest 25 frames across every state (`RecentFrames`), so the panel keeps
    showing `failed` rows. There is no `loadMore`.
- **The seed refreshes every row that has an outcome, in either zone.** A live row whose completion
  was missed during a stream drop would otherwise hold its pre-completion state until a reload. A
  row **still in flight** is the exception: the seed may carry a previous pull's row for the same
  key (a re-adopted frame), and adopting it would show the row as final while it is still copying.
  The seed therefore updates a row that is in the tail or already terminal, and leaves a live
  in-flight row alone.
- **Pending.** On a snapshot with `pending_listed === true`, every entry is upserted as a head row
  (pending unless already terminal). Then any head row of that rig that is absent from the set and
  still pending is moved to `removing` for the exit animation, and deleted after it. Any other
  snapshot touches nothing.
- **Current.** A `current` with no row yet (a page opened mid-transfer) creates a head row.
- **Completion events** set `terminalState` by key, updating in place. `frame.done` or
  `frame.failed` for an unknown key creates a head row. **`frame.deleted` for an unknown key is
  ignored**, so the feed never adds a Deleted row for a frame the operator never saw arrive.
- **Reconnect and backstop.** Discrete events are not replayed after a drop. A `reconnect` event
  therefore re-seeds, and the next authoritative snapshot reconciles pending. A backstop refetch
  runs every 45 s for the fleet feed, refreshing page 1 in place so it never collapses the loaded
  tail, and every 10 s for the scoped panel.
- **Zone dedup.** A key present both live and in a loaded page keeps its head instance, so a live
  row keeps its in-flight state; `loadMore` skips a key already in the map.
- **Trim.** Head and tail together are capped at 2000 rows, oldest first: the tail is trimmed
  before any head row.

Frontend tests (`useFrameFeed.test.ts`) cover ordering (a late completion filed by its transfer
time, two completions ordered by transfer time rather than arrival, live rows kept above completed
ones) and reseeding (a missed completion adopted, an in-flight row left alone).

### 4.6 The feed page and Recent transfers

- **`/feed`** (`Feed.tsx`) renders a virtualised list of `<div>` rows. Each row shows the device
  badge, the thumbnail (§1), the source basename, type, size, and a state cell (`FeedStatus`): the
  dimmed "Pending transfer", the shared `TransferProgress` bar, or a status pill. It also shows the
  When time, and opens the frame detail modal for rows with a persisted frame. Rows animate on
  live insertion and on d1 removal. Mounts and unmounts driven by scrolling are not animated. A
  leaving row stays in the virtualiser's item array, with its measured height, until its
  animation ends (`LEAVE_MS`).
- **Recent transfers** (Devices) keeps its `Table` layout, with no virtualisation. It is fed by
  the scoped engine, so pending frames appear dimmed and turn into a live bar while copying. The
  animation there is best-effort.
- "Pending transfer" is not a `FrameState`, so it is a dimmed inline label, not one of the
  persisted-state pills of `frameStateView`.

### 4.7 Known limitations

- **Failed frames are not in the fleet seed.** `failed` rows have no `pulled_at`, so a failure
  shows live through its event but drops out of the fleet feed on a full reload until it retries
  and lands. The scoped panel does include failed rows.
- **A paused or offline rig's pending rows linger.** Its snapshots carry no `pending_listed`, so
  its pending rows are never d1-removed. The frames genuinely are still waiting, so this is
  correct, but a rig paused for a long time keeps stale rows until it resumes and lists again.
- **A re-adopted frame inside the seed window can make one scroll page skip a row.** The history
  query pages by OFFSET on `id DESC` with `pulled_at ≤ to`. A frame inside the frozen window that
  is re-pulled during the session takes a `pulled_at` after `to` and leaves the set, shifting the
  offset by one. Duplicates are absorbed by the key dedup. Keyset paging (`id < lastLoadedId`)
  would remove the case if it ever matters.

Rejected alternatives:

| Alternative | Why it was rejected |
|---|---|
| Persist discovered frames as `pending` rows | It adds writes to the hot, read-only discovery path, breaks "a `frames` row is a completed outcome", and changes the result set of every frames query (`ListFrames`, `RecentFrames`, `ListTransferHistory`, the summaries). That is a large, reliability-touching blast radius for a presentational feature. |
| A pinned "in progress" zone above a completed list | A frame captured seconds ago should visibly *become* its transferred self in place, not jump between zones. One keyed collection is also simpler. |
| Live rows bolted onto History | History is a server-paginated record scoped to `pulled_at IS NOT NULL`, and an unpaginated live row has no page. |
| Thin events plus a refetch on every completion | Refetching a 200-row window per completion across many rigs is wasteful and races the live pending state. A full-frame payload costs a few lines. |
| Rows fixed at their first-insertion slot | Insertion position differs from the transfer time a row displays. Late completions, slow transfers and reconnects each put an older When above a newer one. |
| A hand-written snake_case map in the rig package | It would duplicate the DTO mapping in a second place to keep in sync. |
| Return an outcome enum from `transfer` | More churn on a reliability-critical signature than a per-cycle set filled by the emit sites. |

## 5. Next-frame cadence prediction

Between transfers, a rig's card can read as idle while the device is exposing on the mount; on a
long exposure, the frame count sits still for minutes. The device captures on a regular cadence
(roughly the exposure plus overhead), so Commander estimates when the **device** will produce its
next frame and shows a small countdown: "next frame ~in 0:42". This is a different fact from
the copy in progress (the transfer bar) and "next poll" (when Commander checks the device), and each
stays on its own line.

The estimate is a hint. Dithers, meridian flips, autofocus runs and filter changes all perturb the
true cadence, so the readout degrades to "no prediction" rather than show a confidently wrong
number.

### 5.1 State machine and the liveness gate

There are two states. **Predicting** is published as a `prediction` object on `RigStatus`.
**Unknown** is the object's absence; the backend never serialises "unknown".

```
Unknown ──(≥1 recent light since local noon, inside the liveness window)──► Predicting
Predicting ──(a light is filed)──► Predicting (recomputed)
Predicting ──(t − last_capture > window and past the ETA, or the observing night rolls over)──► Unknown
```

**The liveness gate is anchored on capture time.** A prediction exists only while
`t − last_capture_host ≤ max(5 × last_exposure, 1 h, interval + last_exposure)`. Here
`last_capture_host` is the newest light's device capture time corrected to host time, and
`last_exposure` is that frame's `Exptime`. The last term is the ETA's lead (§5.2 step 5): a frame
that is not yet due is no sign of a stalled sequence, so the gate never closes before the ETA. It
binds only for a cadence slower than four exposures past the 1-hour floor. Two consequences
follow:

- **A backfill of historical frames never predicts.** Its newest capture is already outside the
  window, even though the row was just filed, so no "am I backfilling?" detection is needed. A
  live session that fell briefly behind and is catching up keeps recent captures, and stays
  Predicting.
- **The window rests on the exposure, not the measured interval.** A legitimate long gap (a flip,
  an autofocus run) inflates a measured interval, and 5× that would keep a dead prediction alive
  for hours. The exposure is a stable property of the last frame. The 1-hour floor dominates for
  exposures under 720 s.

**Overdue is normal, not expiry.** Once the ETA passes, the readout says "due now" or "overdue
15s" and keeps predicting; overhead simply ran long. Only the liveness window ends a prediction.

### 5.2 Estimating the cadence

1. Take the rig's most recent **light** frames with a `dest_path`, deduped by `dest_path` (a frame
   present on both the Udisk and EMMC shares is two rows and one capture, H12, as
   `CountFramesTonight` dedupes), and captured since local noon (§5.5). Order them by capture time
   and keep the last **5** (`predictSampleSize`), which gives up to 4 gaps.
2. **Capture time** is `DATE-OBS` (the capture start), falling back to the device file mtime when
   `DATE-OBS` is absent or unparseable. Both are device-domain. It is never `pulled_at`, the host
   filing time, which a backlog burst would collapse into a false fast cadence.
3. **Interval** is the **median** of the positive consecutive gaps. Five samples let the median
   reject a single dither or autofocus gap.
4. With **one** frame the interval falls back to the exposure, with `sample_count = 1`, and the UI
   renders it softly ("next frame ~soon"), never as a firm countdown. With none there is no
   prediction.
5. **Next expected** is `last_capture + interval + last_exposure`, corrected to host time: when
   the next frame's file should land. The capture time is the exposure start, so
   `last_capture + interval` is when the next exposure **starts**; its file appears one exposure
   later, plus the save and listing lag. Anchoring at the start would read "overdue" for most of
   every exposure, while the anchor at the file's arrival leaves only the lag to show as a few
   seconds overdue. When the capture time falls back to the mtime (step 2), which marks the end of
   the exposure, the ETA errs one exposure late; the ASIAIR writes `DATE-OBS`
   ([asiair-hardware-notes §8.1](2026-10-17-asiair-hardware-notes.md)), so the fallback is rare.

**The clock offset.** `offset = device − host` is measured per SMB session (`internal/clock`).
Both ends of a gap are device-domain, so the offset **cancels** and the interval needs no
correction. The anchor does need it: `host = device − offset`, the same transform
`Clock.YoungerThan` applies. Only the backend knows the offset, which is one reason the prediction
is computed there. Guard: `TestPredictFramesOffsetCancellation`.

### 5.3 Where it is computed

`internal/rig/predict.go` holds the pure maths (`predictFrames`, `cadenceInterval`,
`livenessWindow`, `frameCaptureTime`), with no device, store or SMB dependency. The worker's
`framePrediction` sources the inputs by filtering the rig's 50 most recently filed frames
(`RecentFrames`) in Go, rather than adding a store query, so the capture-time choice lives in one
place and not in SQL. The 50 leave room for interleaved non-lights and two-share (H12) duplicates.
It runs in `publishListingStatus` and in `refreshLiveCounters`, after each filed frame, so the
prediction refreshes exactly when frames appear.

The backend publishes a static `next_expected_ts` (host unix seconds), `interval_sec`,
`last_exposure_sec` and `sample_count`. The countdown ticks in the browser once a second, so there
is no per-second server traffic.

Computing on the backend reuses the two pieces of logic only the backend has: the clock offset
and the observing-night boundary. The snapshot is also what both glance cards, Dashboard and
Devices, already render. Commander's cards render backend-computed status verbatim (`drain`,
`safe_to_power_off`) rather than deriving state client-side.

Guards: `TestPredictFrames`, `TestPredictFramesETAIsNextFileArrival`,
`TestPredictFramesLivenessCoversETA`, `TestFrameCaptureTime`, `TestFramePredictionLiveSession`,
`TestFramePredictionDedupesH12`, `TestFramePredictionBacklogBurstStaysUnknown`,
`TestFramePredictionSessionRollover`.

### 5.4 What the UI shows

`NextFrame` is shared by the Dashboard and Devices cards, so the two readouts cannot drift.

| State | Readout |
|---|---|
| Predicting, ≥ 2 frames, ETA ahead | `Recent frames: 600s · next frame ~in 0:42` |
| Predicting, ETA passed | `Recent frames: 600s · next frame due now` / `overdue 15s` (`overdue 1:30` past a minute) |
| Predicting, one frame | `Capturing: 600s · next frame ~soon` |
| Unknown, online and idle | muted `Waiting for frames…` |
| Unknown while a copy or cleanup is live | nothing (beside a live readout the hint would read as a stall) |
| Offline or paused | nothing (the state pill carries it) |

The ticker exists only while a countdown is showing (`formatCountdown` in `web/src/util/format.ts`).

### 5.5 Edge cases

| Case | Handling |
|---|---|
| A backlog filed in a burst | Cadence uses capture time, so 50 frames pulled in 2 minutes keep their real spread, and the liveness gate keeps an old backlog from predicting at all. |
| Clock offset | Gaps are offset-free; the anchor is corrected once, server-side. |
| Irregular cadence | The median resists one outlier gap; a genuine stop ends at the liveness window. |
| Mixed exposures in one sequence | The median blends the gaps. The readout shows the last frame's exposure, which may differ from the next. This is accepted for a hint. |
| The observing night | Only frames captured since local noon of the observing date (`route.ObservingDate`, in the worker's site zone; see [routing-and-filing §6.1](2026-10-17-routing-and-filing.md)) count, so last night's frames never seed a dusk prediction. Rolling past noon empties the window. |
| First frame of a session | 1 frame gives the soft guess; 0 gives Waiting for frames. |
| The sequence ends | The liveness window flips the state to Unknown rather than counting down forever. |

### 5.6 Rejected alternatives

| Alternative | Why it was rejected |
|---|---|
| Compute in the frontend from `listFrames` | No access to the clock offset; it would duplicate the night-boundary and dedup logic; and the frame list is not loaded on the glance cards. |
| `pulled_at` as the capture time | A backlog burst reads as a false fast cadence. |
| The measured interval as the basis of expiry | A legitimate flip or autofocus gap inflates it absurdly. It only floors the window at the ETA. |
| `last_capture + interval` as the ETA | That is when the next exposure starts, not when its file lands, so the readout reads "overdue" for most of every exposure. |
| Liveness measured from when the row was filed | A backfill would predict. |
| Mean instead of median | One outlier gap skews the mean. |
| Exposure plus a fixed overhead constant as the interval | The overhead is a guess; the measured median calibrates itself and includes the real overhead. |
| Per-(filter, exposure) models, EWMA, Kalman filtering | Over-engineered for a hint. |
| No readout for a single frame | A soft "~soon" is honest and still shows that work is in progress. |

## 6. Device clock sync

An ASIAIR has no battery-backed clock and no NTP client. It boots to its firmware's date and keeps
that until the phone app connects and sets the time ([asiair-hardware-notes
§7](2026-10-17-asiair-hardware-notes.md)). A rig that is powered but never opened in the app
therefore keeps a wall clock that can be years wrong, and every frame it captures carries a
nonsense `DATE-OBS`.

Commander measures the divergence every cycle, it knows which device is which, and the fix is a
short exchange on the device's own control channel. The feature has two parts:

- an **opt-in, per-rig** setting (`sync_clock`) that corrects a configured, guid-bound device's
  clock when it has drifted far enough to matter;
- an offset warning that reports transitions instead of repeating one line per rig per poll for
  as long as the condition stands.

The toggle sits in the Devices editor after *Keep originals*, with help text. Turning it on needs
outbound TCP 4700 from Commander's host to the rig, beside the UDP 4720 and TCP 445 it already
uses.

`sync_clock` needs no config schema bump and no migration: an absent field loads as `false`,
which is the intended default. Previews (§1.6) and plate solving (§3.8) need migrations only
because they seed keys whose default is not the Go zero value.

The app itself sets the clock as its first write on every connection, ahead of any camera or
mount query. Stepping this clock is the vendor's own intended behaviour, not a novel intervention.

### 6.1 Two clock readings, on purpose

The SMB NEGOTIATE offset is the **trigger**; `pi_get_time` is the **authority**.

- The negotiate offset is computed every cycle at no extra cost (`internal/clock`), and compares
  absolute instants, so it needs no zone. It makes the right cheap gate: in the common case the
  offset is small and no control connection is opened at all.
- `pi_set_time` takes a wall-clock date plus an IANA zone, and only `pi_get_time` reports the zone.
  So once the gate opens, the phase reads the clock on the control channel and re-measures the
  offset immediately before writing. A device that drifted back into tolerance between the SMB
  handshake and the control connection is left alone.

**One sign convention everywhere: `offset = device − host`.** A device stuck years in the past has
a large **negative** offset. The control-channel reading uses the same convention
(`controlInstant(reported, loc).Sub(w.now())`), and every log line carries that sign.

### 6.2 One threshold, one meaning

One constant, `clockOffsetThreshold = 5 * time.Minute`, drives both the warning and the sync
trigger. It is not configurable: nothing about the number is rig-specific, and the protocol pins
its floor. `pi_set_time` carries whole seconds, so the residual after a correction is about 1 s,
and any threshold below about 2 s would write on every cycle forever.

The warning reports **transitions**:

| Event | Level | Line |
|---|---|---|
| The offset leaves tolerance | WARN | `rig: device clock offset out of tolerance` (offset, threshold, `sync_clock`) |
| The offset returns to tolerance | INFO | `rig: device clock offset back within tolerance` |
| Commander sets the clock | INFO | `rig: set device clock` (before, after, zone, residual) |

A stuck clock with the toggle off costs one line. With the toggle on, the log tells a complete
three-line story.

The band state (`offsetOutOfBand`) updates **only where an offset was actually measured**
(`recordClockOffset`). A cycle that never opened a session therefore cannot log a false all-clear,
and a rig that goes offline while out of band comes back still out of band, silently, which is the
truth.

**Toggling `sync_clock` resets the latches.** `noteSyncClockSetting` compares the toggle with its
last-seen value. On a change it clears the band latch and the failure cooldown, so enabling the
feature re-announces a standing condition rather than staying silent, and re-enabling it after a
failure retries at once.

### 6.3 The control channel

`internal/control` mirrors `internal/device`: a `Client` interface (`Info`, `AppState`, `GetTime`,
`SetTime`, `Close`), a real implementation, and an in-memory fake with scripted replies, recorded
writes and per-method error injection. The wire facts are in [asiair-hardware-notes
§6](2026-10-17-asiair-hardware-notes.md): port 4700 only, line-delimited JSON-RPC, replies matched
by `id` among unsolicited `Event` pushes, errors as a non-zero `code` with an `error` string, and
`get_app_state` returning the full state object on 4700. The client uses a 3 s dial budget and a 5 s
per-call deadline, with request ids starting at 200 (the app uses low ids; there is no shared id
space, but staying clear costs nothing). The dialer routes through the endpoint's network site,
adding one round-trip margin to both the dial budget and the per-call deadline (both exact on the
local site), so a rig at a remote site is reached through its tunnel ([remote-sites
§3](2026-10-17-remote-sites.md)).

The worker holds the dialer as a `dialControl` field, defaulted inside `NewWorker` and overridden
directly by the package's tests, rather than as another positional constructor parameter. A
signature change would have to reach every `NewWorker` call site, including
`test/integration/refile_test.go`, which sits behind the `integration` build tag and so does not
compile under the default build.

The wire formats this feature depends on are encoded in the `internal/control` tests against a
stub server: a reply after interleaved `Event` pushes (including one carrying the caller's own
id), a foreign id, a non-zero `code`, a truncated line, and `get_app_state` results of the wrong
shape. A firmware change to the wire format therefore breaks a test rather than a rig. On a device
whose clock booted to its factory date, one correction brings it within a second of the host,
the whole-second residual [asiair-hardware-notes §6.4](2026-10-17-asiair-hardware-notes.md)
predicts, and a second run against the corrected device is a no-op.

This is deliberately **not a general control API**: three reads and one write, all serving the
clock. Mount, camera, focuser and plan control stay out. The channel lives in its own package
rather than `internal/discovery`, which owns UDP identity probing. A stateful TCP session with
interleaved pushes is a different transport serving a different concern.

`clockPhase` runs **last** in the cycle, after the SMB session has closed (the two connections
never overlap) and after every device-time comparison the cycle made. Stepping the clock therefore
cannot make one cycle's `min_file_age`, settle and grace arithmetic incoherent. It runs only when
the cycle was not refused and the worker is not suspended, and it is deliberately **not** gated on
keep-originals: setting a clock is not deleting a frame. It runs on the rig's own worker
goroutine, so per-device seriality comes for free.

### 6.4 Confirming identity on the channel itself

`pi_get_info` returns the device's `guid` and `cpuId`, for example
`{"model":"ZWO AirPlus-RK3568 (Linux)","guid":"0a1b2c3d","cpuId":"0011223344556677",…}`. A CM4
reports an empty `cpuId`. The write is guarded by the pull path's identity rule ([device-identity-and-media
§4.1](2026-10-17-device-identity-and-media.md)): the guid matches, or the cpuIds match when both
are non-empty. That rule is checked **on the connection that will carry the write**, so there is
no window in which the address could have moved to another device since an earlier probe. Two
empty cpuIds never match each other.

The check is stricter than the pull path in one respect: a rig with **no bound guid** is skipped
outright. Reading from a device Commander cannot name is tolerable; writing to one is not. Config
validation raises a warning on `rigs[<id>].sync_clock` for such a rig, so the refusal surfaces as
advice rather than a silent skip. The unbound check runs before the cooldown check, so an unbound
rig cannot log a line every cycle.

### 6.5 Only this cycle's measurement

The offset the phase gates on (`cycleOffset`) is measured during the current cycle and reset at the
top of `pullPhase`. An offset that was never measured, because the cycle refused before opening a
session, is the zero value and fails the threshold. No reading from an earlier cycle can authorise
a write against a device whose situation has since changed, so the use site needs no freshness
caveats. The failure cooldown is the one state that deliberately outlives a cycle.

### 6.6 Fail-closed

Exactly one path ends in a write, and it requires every one of these:

- the toggle on;
- a bound guid;
- an offset past the threshold;
- no cooldown;
- identity confirmed on the channel;
- every subsystem idle;
- a resolvable zone;
- a re-measured offset still past the threshold.

**Every other outcome — any error, timeout, refusal, ambiguity, or sign of activity — closes the
connection and changes nothing.** This is a property of the code's shape: the phase has one
`SetTime` call site, reached only after the checks pass in sequence, and every failure branch
returns. The phase returns nothing, so no caller can act on its outcome, and it runs under the
cycle's panic recovery. A correct clock is a convenience; an undisturbed rig is not.

After a successful write the failure latches clear, whatever the confirming `pi_get_time` returns.
The correction has landed, and treating a failed confirmation as a sync failure would start a
cooldown against a device that is right.

### 6.7 Idle-only

Commander never steps the clock under an imaging session. Idleness has exactly one source: the
device's own `get_app_state`, asked on the connection that will carry the write. The verdict is
**generic**:

- any top-level object carrying `"is_working": true` means busy, and so does a `capture.state`
  other than `"idle"`;
- firmware that adds a subsystem is respected with no code change;
- it is **fail-safe**: a reply that arrives but does not parse counts as busy ("unreadable app
  state"), returned as a verdict with a nil error.

A reply that never arrives is a **transport failure**, not a busy device, and takes the cooldown
path. Treating a hung port as "busy" would retry it every cycle forever.

Two tempting shortcuts are unavailable. No method reports connected clients. `connect_lock` is a
stored pairing preference, not a live connection indicator ([asiair-hardware-notes
§6](2026-10-17-asiair-hardware-notes.md)). And **elapsed time since the last frame proves
nothing**: sub-exposures run from 15 seconds to an hour, and a rig pauses between them for filter
changes and autofocus, so no quiet window is safe, and the error lands in the dangerous direction.

Idleness is also the stronger gate. An app can be connected and idle, where stepping the clock is
exactly what the app does on connecting, or connected and running a plan, which is the case that
matters. In practice the gate almost never fires. An ASIAIR does not start capturing on its own: an
app connects to start a plan, and the app sets the clock as its first act on connecting. A device
more than five minutes out is therefore one no app has talked to since it booted, so it cannot be
imaging. The check guards the residual case, an app that connected carrying its own wrong time and
is running a plan.

### 6.8 Timezone resolution

Commander writes the current time in **the zone the device reported**, so syncing a rig at a remote observing
site never drags it into the Commander host's zone. `cmd/asiair-commander` imports
`time/tzdata`, which embeds the tz database. This works identically on Windows, which has no
system tz database outside a Go installation, and in a distroless image. An empty zone is refused
before `time.LoadLocation`, which would answer `""` with UTC and a nil error. A zone the embedded
database does not know is refused too. Both are logged with the zone, and nothing is written:
guessing would silently move the rig's wall clock by hours.

### 6.9 Failure handling and backoff

- A failed attempt, meaning any transport or protocol error at any step (dial, `pi_get_info`, an
  identity mismatch, `get_app_state`, the pre-write `pi_get_time`, `pi_set_time`, an unusable
  zone), sets
  a per-rig cooldown of `clockSyncRetryAfter = 30 * time.Minute`, held in worker memory. A device
  that accepts a connection and then hangs is a failure like any other. The confirming
  `pi_get_time` after a successful write is not on this list: its failure logs
  `rig: set device clock, could not confirm` at INFO and starts no cooldown (§6.6).
- Only the first failure after a success, or after the toggle changed, logs at WARN
  (`rig: clock sync failed; backing off`, naming the step). Attempts suppressed by the cooldown log
  at DEBUG.
- **A busy device is not a failure.** It is the one decline that starts no cooldown: it is skipped
  at DEBUG and retried next cycle, because a plan may end at any time.
- A failure never raises an alert: an opt-in cosmetic correction failing is not an operator
  emergency, and an alert would stand until acknowledged.
- Escalating after repeated failures is rejected too. A device that will not answer, or answers
  with the wrong identity, is one Commander should leave alone.

### 6.10 What a corrected clock does to timestamp math

Files already on the device keep the mtimes they were written with. Neither consequence needs code:

- **Device behind (the common case).** Existing frames keep their old mtimes and are, in device
  time, ancient: instantly past `min_file_age` and every settle window. The measured offset had
  already made the arithmetic consistent before the sync, so nothing changes.
- **Device ahead (rare).** Frames written while the clock ran fast carry future mtimes. After
  correction, `min_file_age` is not satisfied until wall time catches up. The delay is bounded by
  the size of the correction and heals itself. A device more than five minutes ahead requires an
  app to have set a wrong time.

Already-captured frames are never retro-dated: their `DATE-OBS` stays as written. The measured
offset is not published on `RigStatus`; it feeds the cadence prediction (§5.2) and this phase. The
`AlertClockSkew` category concerns the **host's** wall versus monotonic clock and is unrelated.

### 6.11 Invariants

Cite these doc-qualified ("features I6").

| # | Invariant | Proven by |
|---|---|---|
| I1 | `pi_set_time` is never sent to a device whose `pi_get_info` identity does not match the rig's bound guid/cpuId, including a rig with no bound guid. | `TestClockPhaseRefusesForeignDevice`, `TestClockPhaseRefusesUnboundRig`, `TestClockPhaseAcceptsCPUIDFallback`, `TestClockPhaseEmptyCPUIDIsNotAMatch` |
| I2 | With `sync_clock` off, its zero value, no control-channel connection is ever opened. | `TestClockPhaseNeverDialsWhenDisabled` |

| I5 | No control-channel outcome alters the pull, restore or delete phases, or fails the cycle. | Structural: `clockPhase` returns nothing and runs last, so no caller can read its outcome. |

### 6.12 Rejected alternatives

| Alternative | Why it was rejected |
|---|---|
| `pi_get_time` as the trigger too | A TCP connection to every managed rig every poll, to evaluate a condition that is almost always false. The SMB offset is already measured and free. |
| Shift the reported wall clock by the SMB offset, skipping the zone lookup | A multi-year correction crosses DST transitions, so adding a duration to a wall-clock reading in an unknown zone lands up to an hour off. That is still past the threshold, so it would never converge. |
| Set the clock every cycle, with no threshold | `pi_set_time` carries whole seconds, so this means continuous writes to a device for no observable gain. |
| A configurable threshold, per rig or global | Nothing about the number is rig-specific, and the protocol pins its useful floor. A setting nobody should change. |
| A separate one-minute warning threshold | Two numbers meaning almost the same thing, plus a 1–5 minute band that warns forever and is never acted on. |
| Gate on `connect_lock` | It is a stored pairing preference, false throughout a session with the app actively connected. |
| Gate on "no app connected" | No method reports clients, and idleness is the stronger property. |
| A quiet-window pre-gate on time since the last frame | Elapsed time cannot tell idle from mid-exposure; it is at best evidence of activity, never of idleness. |
| Trust the cycle's earlier scan_air identity probe | It leaves a window between the UDP probe and the TCP connection. One extra round trip removes it. |
| A timezone override | No user needs it; preserving the device's own zone is correct for every case. |
| One global on/off switch | Rigs differ: one is opened in the app nightly, another sits headless for weeks. Per-rig booleans are the existing pattern (`keep_originals`, `pull_logs`). |
| Apply to discovered but unadopted devices | Commander would be writing to hardware it does not manage. |
| The channel in `internal/discovery` | A different transport serving a different concern. |
| Sync before or during the pull phase | It would invalidate the offset that cycle uses for every `min_file_age`, settle and grace comparison. |
| Raise an alert on failure | See §6.9. |

### 6.13 Non-goals

- Devices that are discovered but not adopted are never touched; the setting lives on a configured
  rig.
- Already-captured frames are not repaired.
- There is no general device control: three reads and one write, for the clock only.
- There is no timezone management: the device's zone is preserved, never chosen.
- There are no metrics, alerts, status fields or manual "sync now" action. The feature reports
  through the log, plus the one config-validation warning of §6.4.

## 7. Newer-release indicator

Commander has no self-updater: a Windows install is upgraded by running the next installer, a
container by pulling the next image. An operator who does not follow the repository has no way to
learn that a release exists. The nav therefore shows a small link next to the version when a
release newer than the running build has been published. It is advisory: nothing is downloaded or
installed.

### 7.1 The check

`internal/updatecheck` asks `GET https://api.github.com/repos/macourteau/asiair-commander/releases/latest`,
unauthenticated, and reads `tag_name`. That endpoint excludes drafts and prereleases, so the
`astap-cli-<version>` mirror prereleases never count. A tag counts only when it is a clean
`vMAJOR.MINOR.PATCH` that is semver-greater (`golang.org/x/mod/semver`) than the running version.

- **Release builds only.** A build whose version is not a clean release — `dev`, unset, a bare
  commit hash, a `git describe` build between tags (`v1.2.3-4-gabcdef`, which semver reads as a
  prerelease) — never schedules a check. This matches the SPA's version banner, which is inert for
  `dev`/unset builds.
- **Schedule.** The first check runs a uniformly random 1–10 minutes after startup, so a fleet
  restarted together (a host reboot, a watchtower pull) does not ask at the same instant and a
  crash-looping process does not spend the rate limit. Each later check follows after 60 minutes
  ± up to 5, drawn per interval. One request an hour sits well inside GitHub's unauthenticated
  limit of 60 an hour per address. The loop ends with the application context.
- **Request.** A 15-second timeout covers the whole exchange, the `User-Agent` names the app and
  its version (GitHub requires one), and the body read is capped at 1 MiB.
- **Fail-open.** Any failure — network, a non-200 (rate limit included), malformed JSON, a missing
  or non-release tag — is logged at debug and changes nothing: the last successfully fetched
  answer stands. A successful answer that is not newer (a newer release was deleted, so
  `releases/latest` fell back to an older tag) clears the indicator, because that tag is
  semver-lower. The answer lives in memory only and is never persisted.

### 7.2 The switch

`update_check_disabled` (top level of `config.yaml`, default `false`) stops the check. It is named
for the off state, like `Source.Disabled`, so a config that predates the key loads with checking
on: no schema bump and no migration, and an older binary ignores the key. The whole-config PUT
carries it as a pointer shadow (beside `mosaic_detection`), so a stale tab whose body lacks the key
cannot switch a disabled check back on.

It applies live. The checker reads the switch from the live config pointer at every tick, and
`Latest` reports nothing while it is off, so the indicator hides at once. A save that flips the
switch re-announces `server_info`. A value learned before the switch was turned off is kept and
reappears when it is turned back on: it is still a published release, and the next tick refreshes
it. The Settings page shows the switch under *Updates*, with help text naming the hourly request to
api.github.com.

### 7.3 Delivery

The result rides the SSE `server_info` event ([architecture §8.9](2026-10-17-architecture.md)) as
`latest_version`, empty for none. A change (a check finding a new value, or the switch flipping)
emits a fresh `server_info` through the hub to every connected client, so no client polls. The SSE
handler subscribes to the hub before it writes the initial `server_info`, so a re-announcement
racing a connect is queued rather than lost.

The nav renders the link only when `latest_version` is set and differs from the server's running
`version`. It compares against what the server runs, not the tab's `__APP_VERSION__`: the
indicator is about what is installed, and a tab older than its server is the version banner's
concern. The link opens `https://github.com/macourteau/asiair-commander/releases/latest` in a new
tab (`rel="noopener noreferrer"`), with an accessible label naming the version.

The base URL is injectable for tests. Outside them, only a `-tags demo` build can redirect it (the
`AC_DEMO_RELEASES_URL` environment variable, for UI passes against a local fake); the production
binary has no flag or variable that points the check anywhere but api.github.com.

### 7.4 Rejected alternatives

| Alternative | Why it was rejected |
|---|---|
| Poll GitHub from the browser | Every open tab would query on its own schedule, each browser would disclose itself to a third party, and the switch would have to be enforced in every client. One server-side check an hour, pushed over the stream the SPA already holds, costs nothing per tab. |
| Persist the last answer | A file and a format to maintain for a value that is cheap to re-learn: a restart re-asks within ten minutes. A persisted answer would also outlive the facts it was drawn from, such as a release deleted while the service was down. |
| A pulled or yanked release signal, telling installs to roll back | A downgrade is unsafe. The state store refuses a schema newer than its binary ("newer than this binary understands", `internal/store/store.go`), as the config loader does, so an install that ran a bad release cannot open its data under the previous one. A bad release is fixed forward with a new version. Deleting a release needs no signal either: `releases/latest` falls back to an older, semver-lower tag, so the indicator simply hides. |
| Compare against the tab's `__APP_VERSION__` | That is what the tab loaded, not what is installed; skew between the two is already the version banner's job. |
| A positive `update_check: true` key | Defaulting an absent key to on would need a schema bump and a migration, and a bumped schema is refused by every older binary. The negative name makes the zero value the default. |
| An authenticated request | A token would have to be provisioned on every install for a request that fits the anonymous limit. |
| Check on every startup, without a delay | A crash loop would spend the rate limit, and a fleet restarted together would ask at the same instant. |
