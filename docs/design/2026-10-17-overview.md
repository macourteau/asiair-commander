# ASIAIR Commander — overview

**Scope.** This is the product contract that every other design document assumes. It covers the
problem Commander solves, what it does on a normal night, why the copy is proven before any
original is deleted and why that proof cannot be switched off, the principles every mechanism
answers to, what Commander deliberately does not do, and the glossary the other documents use
unchanged. It holds no mechanism detail. Each section links to the document that owns the
mechanism, and §10 maps the whole set.

## 1. The problem

An imaging rig built around a ZWO ASIAIR writes every frame to the device's own storage: an
internal eMMC, a TF card, or a USB stick. The frame stays there until someone fetches it. An
operator with several rigs ends up with a manual routine for each rig, every night: pull the
stick, carry it to a computer, and paste each night's frames into the right folder. Or the
operator offloads the device over Wi-Fi the next morning, one rig at a time, as one long bulk
copy.

There are two separate problems here.

- **Labour.** The pull, carry and paste routine has to be repeated for every rig and every
  night, and the folder a frame belongs in has to be chosen by hand.
- **Capacity.** A unit with 32 GB of eMMC has roughly 20 GB free. A short summer night writes
  about 4.5 GB and a long winter night about 9 GB, and a calibration run (a hundred bias frames,
  10–20 flats for each of seven filters) can use a large share of that space before imaging
  starts. Two large nights fill the device, and a full device stops capturing.

The usual stopgap, a copy script, adds a third problem: it does not verify anything. A script
that reports success when its copy loop finishes, and then offers to delete the originals, has
never compared what it wrote with what it read.

The goal is a NAS that already holds the night's data when the operator wakes up, filed where
the stacking software expects it, so the operator can shut the rigs down and start processing.
No copying, no carrying and no pasting. Every original is deleted only once its copy is proven,
so the device never fills.

## 2. What Commander is

Commander is a single Go service with an embedded web UI. It starts with the machine and runs
unattended, whether or not anyone is logged in, on an always-on machine on the same network as
the rigs: as a Windows service installed by the Windows
installer, or as a container image published on ghcr.io. It watches every configured ASIAIR
over SMB1, pulls each captured frame shortly after the device writes it, proves the copy byte
for byte, files it into a folder layout derived from the frame's own FITS header, and, once the
copy is proven, deletes the original.

There is no server on the far end, no cloud and no second copy anywhere else: the pull is the
write. That
is why read verification is the safety mechanism everything else rests on (§4).

The web UI is the only window into Commander and the only way to configure it. It works from
any browser on the LAN, including a phone at the scope. Commander can delete the operator's
data, so the UI is password-protected. First-run setup is authorised by a one-time setup token,
and HTTPS is served on the next port up, next to plain HTTP
([architecture §8.2](2026-10-17-architecture.md), [§8.5](2026-10-17-architecture.md)). Rigs at
another location are reached through a paired remote at that site
([remote-sites](2026-10-17-remote-sites.md)).

Frames travel from the ASIAIR over Wi-Fi or Ethernet to the machine Commander runs on (through
the remote's tunnel for a rig at another site), and are written to one destination volume that
holds the staging, light and cal roots together, so filing is a rename and a frame is never
transferred twice.

The runtime shape, threading model and persistence are in
[architecture](2026-10-17-architecture.md).

## 3. A normal night

**Once per rig.** The operator adopts the rig in the web UI. Commander finds ASIAIRs on the
network by their own discovery broadcast, both on demand (Scan) and in the background, so a
device that has just been switched on is already listed as found the next time the UI is open
([device-identity-and-media §2](2026-10-17-device-identity-and-media.md)). The operator fills in
the rig's profile: a name, the OTA mounted on it, the shares and roots to pull from, and where
lights and calibration frames go. The operator turns management on and saves.

From then on Commander looks after the rig whenever it can reach it. A rig is **managed until
paused**. There is no nightly arming step and no per-session button, because calibration frames
are taken at dusk, before imaging, and the point is to touch the tool as little as possible. A
per-rig pause and a global pause cover unusual sessions, and both survive a restart. **Run
now** forces an immediate cycle; on a paused rig it runs until the rig is idle and then stays
paused.

**From dusk through the night, unattended.** Each managed rig has its own loop. It runs a cycle,
waits the poll interval (45 s by default), and runs the next; the loop is the same whether it is
pulling flats at twilight or lights at 3 a.m.:

1. Probe the device. A rig that is switched off or out of range is a normal state, not an
   error: the cycle is skipped quietly and retried later.
2. Connect, confirm that the device answering is the rig's own device, and list the configured
   sources.
3. Pick out the frames Commander has not pulled yet that have finished being written. A frame
   must be old enough and must have stopped changing before it is pulled.
4. Pull each frame, hashing every byte as it streams, and check the byte count and the source
   against what the device listed.
5. Flush the staged copy to disk and read it back to prove it at rest, then file it on the NAS
   in the layout of §5 with an atomic same-volume rename, so a power cut can never leave a
   half-written file that looks complete.
6. Delete originals whose copies were proven at least a grace period ago, after one more
   comparison (§4).
7. Disconnect. No session is held open between cycles.

Cycles of one rig never overlap and never pile up. A large backlog makes one cycle longer, and
the next cycle starts after it ends. The full sequence, step by step, is
[frame-lifecycle](2026-10-17-frame-lifecycle.md).

**Starting late is normal.** If Commander starts, or a rig comes into range, after the session
began, frames are already waiting. There is no bulk mode and no live mode. The first cycle is
simply a large one, and the loop then settles into a trickle.

**By morning.** Each rig's card shows what it did, and two separate answers:

- **Safe to power off.** Everything on the device has been pulled and proven on the NAS, so
  shutting the rig down at that point loses nothing. A frame captured minutes before shutdown
  may still be inside its quiescence window and not yet pulled, so this verdict is conservative
  and can read Working or Unknown, with a reason.
- **Drained.** The originals have been deleted and the space is free, or the card shows how many
  originals are still on the device.

The two differ because of grace: a frame can be safe on the NAS while its original waits out
its grace on the device. On a capacity-bound rig that difference is what matters most. "Safe"
means no data loss; "drained" means the space has actually been freed. Both verdicts are
defined in [frame-lifecycle §14](2026-10-17-frame-lifecycle.md).

## 4. Proving the copy before deleting the original

An ASIAIR cannot be asked for a checksum. It lets a client list files, read them and delete
them, and nothing more, so nothing in the system can give an independent second opinion. If
Commander read corrupted bytes off the device, it would hash the corruption faithfully, write
it to the NAS faithfully, and every check that compares the copy with itself would pass. The two
copies would match each other, both would be wrong, and the good original would be deleted.

The only thing that catches that failure is a **second read of the device** compared with the
first. Commander therefore makes three comparisons before its normal cleanup deletes an original
whose NAS copy is still present:

- the hash streamed during the pull;
- a cache-bypassing read-back of the staged copy, made before it is filed
  ([frame-lifecycle §6](2026-10-17-frame-lifecycle.md));
- a fresh hash of the device original, taken by the delete pass, which must equal the recorded
  device anchor, while a fresh re-hash of the NAS copy must equal the recorded archive anchor
  ([frame-lifecycle §9.2](2026-10-17-frame-lifecycle.md),
  [delete-safety §4](2026-10-17-delete-safety.md)).

> **If deletion is enabled, verification happens. There is no off switch.**

The exceptions are operator decisions, not settings. When the operator has deleted a frame's NAS
copy (a cull), there is no copy left to re-hash, so the original goes after its settle window or
an Acknowledge, once a fresh device hash matches the recorded one. The file browser deletes
exactly what the operator confirmed, archived or not. Every such path and its guard is listed in
[delete-safety §3.1](2026-10-17-delete-safety.md).

A system with a server on the far end, one that checksums what it receives independently, can
afford to make verification optional. Commander has no such server, so the second read is the
only witness it has.

**The cost is small.** Reading every frame twice is expensive only when a whole night is pulled
at once, which is the routine Commander replaces. Spread across the night, one 120 MB frame
roughly every ten minutes, read twice, is about **0.4 MB/s**. On a link of around 12 MB/s that
is about 3% of the link for one rig, and about 20% with six rigs working. Draining overnight is
what makes integrity checking nearly free, so the two goals are served by one design. Link
speeds and frame sizes are in [asiair-hardware-notes §10](2026-10-17-asiair-hardware-notes.md).

**When deletion happens.** Rigs are usually powered only at night, so a grace period of a day
does not delay deletion by a day. It defers it to the next night, the next time the device can
be reached. On a winter night, night one's 9 GB would then stay on the device until partway
through night two, a peak of about 18 GB against 20 GB free. On a capacity-bound rig, grace has
to be short enough to expire **within the same session**. A rig with a large USB stick (124 GB
holds about 13 such nights) has no such pressure and can take a long grace as a safety margin.

Grace is therefore a **per-rig setting**, with a default of **1 h**. A longer grace makes the delete
pass's second device read more independent of the first
([delete-safety §4](2026-10-17-delete-safety.md)); a shorter grace frees capacity sooner. The copy
is proven on the NAS independently of grace, so a short grace weakens only the detection of a
transient device read fault, never the guarantee that a good copy exists. A grace of zero is
rejected whenever deletion is enabled, because a re-read immediately after the pull proves
nothing. A rig set to keep originals never runs the delete pass and has no grace to enforce. The
mechanism and the tuning are in [frame-lifecycle §9.3](2026-10-17-frame-lifecycle.md) and
[architecture §16](2026-10-17-architecture.md).

## 5. Where each frame goes

Every FITS frame carries a header at the front of the file. It states what the frame is: frame
type, target, exposure, set-point temperature, filter, camera, gain, binning and capture time.
Commander reads that header from its own verified copy after the pull and files the frame by
it. It never infers what a frame is from the folder or the filename on the device.

The rule is: **read the header, decide what kind of frame it is, and file it into a folder built
from that kind's template.** The templates ship with defaults and are editable. Each frame class
has its own template rather than its own code path: routing is a small set of templates keyed by
frame class, not a general rules engine.

| Frame class | Shipped template | Under |
|---|---|---|
| Light | `<TARGET>/<OTA>/<SESSION>/NIGHT_<n>` | the light root |
| Dark | `<SENSOR>/DARK/<GAIN>/<BINNING>/<SET-TEMP>/<EXPOSURE>/<DATE>` | the cal root |
| Flat | `<SENSOR>/FLAT/<OTA>/<GAIN>/<BINNING>/<DATE>` | the cal root |
| Bias | `<SENSOR>/BIAS/<GAIN>/<BINNING>/<SET-TEMP>/<DATE>` | the cal root |

Lights are organised by what was shot. Calibration frames are organised by the gear, because a
dark or a bias is a property of the sensor and can be reused for every target shot with it. A
flat corrects the optical train, so it also carries the OTA. Gain and binning keep a gain-100
dark from landing next to a gain-0 dark. Temperature groups by the set-point, never the
measured sensor temperature, because a sensor that undershoots its set-point would otherwise
scatter matching darks across many nearly equal values.

Each `<TOKEN>` is filled from one of three sources. Most come from the frame's own header. The OTA
and the session folder name come from the rig profile, because the ASIAIR's `TELESCOP` card names
the mount, not the scope. `NIGHT_<n>` is derived by Commander: nights are numbered in order of
observing date for that target on that OTA, and a date that is new to Commander adopts an existing
night folder holding it before a fresh number is taken ([routing-and-filing
§6.4](2026-10-17-routing-and-filing.md)). An observing date runs noon to noon, so a session that
runs past midnight stays one night, and because the header's capture time is in UTC it is converted
to the host's local time zone before the night is decided. An assigned night is never renumbered.

The frame type comes from `IMAGETYP`, whose values are not standardised across capture software.
They pass through an editable alias table into one of `LIGHT`, `DARK`, `FLAT` or `BIAS`. **A value
the table does not know is never guessed.** The frame is byte-verified, filed into the unclassified
quarantine area, alerted on, and never deleted from the device by the normal delete pass. Its
original goes only once the operator resolves it, by re-classifying it or by culling the quarantine
copy ([library-reconciliation §11](2026-10-17-library-reconciliation.md)). The same applies when a
template needs a header value the frame lacks or cannot map, such as an `INSTRUME` with no entry in
the editable sensor map that turns it into `<SENSOR>`. Only lights get a night number; calibration
is filed by date. An optional token that is simply absent, such as `<FILTER>` on a one-shot-colour
camera, collapses instead of failing.

The roots Commander pulls from are per-rig configuration too: each rig lists the shares and the
roots within them to watch. Because classification, not location, decides the destination,
mosaics, plans, autorun sequences and calibration runs need no special cases. A USB-primary rig
should watch its internal storage as well, because the ASIAIR silently fails capture over to
eMMC when the stick drops out mid-session (hardware finding H12). The two halves of that
session file into the same folder, because both are filed by their headers.

Commander builds the raw-calibration layout and files raw calibration frames into it. The
master calibration files the operator stacks, and any per-target folder that holds them, belong
to the operator. Commander does not create, choose or touch them (§8).

The classification rules, the token table, path safety, night numbering, opt-in mosaic panel
grouping, re-filing and retargeting are in
[routing-and-filing](2026-10-17-routing-and-filing.md).

## 6. All the rigs, at once

Every rig runs its own independent loop. Rigs do not queue behind one another and do not
compete: at a few percent of the link each, there is little to compete for. A global cap on
concurrent transfers (three by default) bounds the load on the NAS and its network as a whole
([architecture §3.4](2026-10-17-architecture.md)).

Against a single rig, the harvester works through one connection and one file at a time, in order,
because the device is busy capturing while it is read: parallel reads have never been shown to help,
and hammering a rig mid-run risks upsetting the capture ([asiair-hardware-notes
§10.3](2026-10-17-asiair-hardware-notes.md)). Transfers run in parallel across rigs and never within
one rig, and there is no setting to change that. The file browser, an operator-driven tool with its
own sessions, is the one deliberate exception
([device-file-browser](2026-10-17-device-file-browser.md)).

## 7. Principles

The principles below hold for every mechanism in the other documents. Two statements of scope
frame them.

- **Commander is built for every operator, not for one setup.** A fix for a safety problem is
  automatic, not a setting someone has to know to turn on.
- **The trust boundary is a trusted LAN.** ASIAIRs expose a guest SMB share that accepts any
  password (hardware finding H11), so a malicious host on the same network segment can already
  read and delete their files directly. Commander's own guards defend against a remote attacker
  without LAN presence, such as one who makes the operator's browser act as a proxy through
  drive-by CSRF or DNS rebinding, and against benign failures such as DHCP address reuse. The
  one LAN-side threat Commander does close is first-run setup: before a password exists, any LAN
  client that reached it first could set one and take the service over, which the setup token
  prevents ([architecture §8.2](2026-10-17-architecture.md)). The threat model is in
  [device-identity-and-media §5](2026-10-17-device-identity-and-media.md), and the web layer's
  share of it in [architecture §8](2026-10-17-architecture.md).

### 7.1 Never lose a frame

The original on the device is the only copy until Commander has proven its own. Every path that
removes a file, whether on the device or on the NAS, is gated either by proof that a good copy
exists elsewhere or by an explicit operator decision: a cull past its settle window or acknowledged,
or a file browser delete the operator confirmed ([delete-safety §3](2026-10-17-delete-safety.md)). A
frame Commander cannot account for is kept and alerted on, never quietly forgotten. A frame that
vanished from both the device and the NAS raises a frame-lost alert. Commander never writes over a
file it did not choose to replace: filing claims names atomically and never overwrites
([frame-lifecycle §8](2026-10-17-frame-lifecycle.md)).

### 7.2 Verification has no off switch

Normal cleanup depends on the three comparisons of §4, and no configuration value disables them. The
operator-driven deletes that cannot run all three are listed in [delete-safety
§3.1](2026-10-17-delete-safety.md). Settings can change how soon an original goes (grace), whether
originals go at all (keep originals), and how long a culled frame's original waits (the settle
window). They can never change whether a deletion is proven ([delete-safety
§2.1](2026-10-17-delete-safety.md)).

### 7.3 Every state is visible on the card

Every state a rig is in appears on its card, including transient and overridden states:
pausing, cleaning up N of M, paused but running until idle, draining, a requested change not yet
applied. None of them is an internal-only flag. A verdict that cannot be given says why (the
power-off reason). When a design adds worker state that changes behaviour, the default is to
publish it and render it ([frame-lifecycle §14.3](2026-10-17-frame-lifecycle.md)).

### 7.4 The UI never waits on a device

No HTTP request blocks on SMB, on a device, or on a rig's cycle. Each rig's device I/O runs on
that rig's own goroutine. The UI reads published snapshots and queues commands, and the worker
applies them between files. A slow, hung or unreachable device therefore never stalls the
dashboard or another rig ([architecture §3](2026-10-17-architecture.md)).

### 7.5 Doubt fails closed

When Commander cannot establish a fact a decision needs, the decision is no: no pull, no delete,
no verdict of "safe".

- A device that does not confirm its identity is not pulled from or deleted on
  ([device-identity-and-media §4.3](2026-10-17-device-identity-and-media.md)).
- An error is never read as an absence. Only a successful listing followed by an authoritative
  stat makes a file absent ([delete-safety §2.3](2026-10-17-delete-safety.md)).
- A destination root without its matching library marker is never reconciled
  ([library-reconciliation §2.4](2026-10-17-library-reconciliation.md)).
- An incomplete or stale listing makes the power-off verdict Unknown rather than Safe.

### 7.6 A frame is filed by what it is, not where it sat

The FITS header decides a frame's class and destination (§5). The device folder it came from,
its filename, and the share it landed on do not. That is what lets one loop handle lights,
calibration runs, mosaics and split-medium sessions, and what keeps a frame Commander cannot
classify out of the wrong folder.

### 7.7 The operator's rules are honoured, never second-guessed

Once a frame is proven on the NAS, the original on the device is working storage waiting to be
cleaned up. The operator's deletion rules (grace, keep originals, the settle window) set when
that happens. Commander applies them as set. It never re-pulls a frame the operator deleted
from the NAS unless the operator asks it to restore that frame, never deletes earlier than the
rules allow unless the operator explicitly asks for it (Acknowledge), and never withholds a
deletion they schedule because it judges the operator's choice unwise. Opt-in behaviours (mosaic
detection, clock sync) stay off until the operator turns them on. The principle that the NAS
copy is the safe place is owned by [delete-safety §2.2](2026-10-17-delete-safety.md); its
application to culls is [library-reconciliation §1.1](2026-10-17-library-reconciliation.md).

## 8. Non-goals

Each of these was considered and rejected for the reason given. They are recorded so they are
not proposed again. Architecture-level rejections are in
[architecture §13](2026-10-17-architecture.md).

| Not built | Why |
|---|---|
| A tray icon, or "ASIAIR detected, start transferring?" pop-ups | A service has no desktop to draw on, and a prompt at 3 a.m. goes unanswered. The web UI serves that role from any device. Consent is given once, by turning management on. Background discovery still lists devices it has found; only the pop-up is rejected. |
| Polling driven by exposure time | Listing a directory costs a few KB against 120 MB frames, on a link that is mostly idle. A fixed per-rig poll interval is simpler and costs nothing. The next-frame prediction on the card is display-only ([features §5](2026-10-17-features.md)). |
| Priority transfers for live stacking | Frames reach the NAS shortly after they quiesce, and nothing queues behind anything, so there is nothing to prioritise over. A live stacker that watches the destination picks them up. Sharing the destination with the stacking machine is the operator's NAS setup, not Commander's. |
| Parallel transfers from one rig | See §6. |
| Resuming a half-transferred file | A broken transfer is discarded and pulled again whole on the next cycle, about ten seconds at 120 MB. Resume logic offers many ways to be subtly wrong in exchange for those seconds. |
| A calibration-session transfer mode | The normal loop already pulls anything that has quiesced, per-rig grace already controls how fast originals go, and header classification files a flat as a flat. A twilight calibration run is the same loop. |
| Managing master calibration files | Commander files raw calibration frames. The operator builds masters and places them, and Commander does not guess at master selection. Copying the right masters into a target's folder automatically is left out of scope, not ruled out. |
| Push notifications (e-mail, chat, webhooks, browser notifications) | Alerts are shown in the web UI only, and only for problems. They are raised from Commander's own state: a failed transfer or verify, an unclassified frame, a filling disk, a managed rig unreachable for too long, and the rest of the catalogue in [architecture §10](2026-10-17-architecture.md). |
| Parsing session logs | A per-rig toggle pulls the guiding log and the session log and files them for support use. Commander does not analyse them. Alerting on log content would be a separate layer above the log store ([architecture §11](2026-10-17-architecture.md)). |

## 10. How the design documents fit together

The documents in `docs/design/` describe the system as it is. This overview is read first, then
architecture, then whichever mechanism a change touches. A contributor changing anything that
can remove a file reads delete-safety before anything else.

| Document | What it owns |
|---|---|
| [overview](2026-10-17-overview.md) | The product contract, the principles, the non-goals and the glossary. |
| [architecture](2026-10-17-architecture.md) | How Commander is built: runtime shape, the never-block threading model, seams, persistence, the web layer (authentication, first-run setup, CSRF and Host checks, dual-port HTTPS, SSE), UI surfaces, the alert catalogue, session logs, the failure model, testing strategy, tuned parameters, metrics, logging and packaging. |
| [frame-lifecycle](2026-10-17-frame-lifecycle.md) | One rig, one cycle, end to end: probe, connect, list, decide, pull, verify at rest, classify, file, the delete pass and disconnect; device-side revision and supersede; delete-pass slicing; dismissing a stuck frame; the Safe-to-power-off and drained verdicts. |
| [delete-safety](2026-10-17-delete-safety.md) | Every path that removes a file and the gate that guards it, the content-hash check and its anchors, listing completeness, the data-loss invariants, where every other invariant series lives, the accepted residual risks, and the checklist for reviewing a delete-path change. |
| [device-identity-and-media](2026-10-17-device-identity-and-media.md) | Discovery, binding a rig to a device, the per-session identity probe, the trusted-LAN threat model, the removable-media marker, removable slots and the presence oracle, and disabling a share. |
| [library-reconciliation](2026-10-17-library-reconciliation.md) | What happens when the operator culls a filed frame from the NAS: the missing mark, the library marker, restore, the culled-original delete, Acknowledge and the cull drain. |
| [routing-and-filing](2026-10-17-routing-and-filing.md) | How the FITS header decides where a frame is filed: classification and quarantine, templates and tokens, path safety, night numbering, mosaic panels, re-filing and retargeting. |
| [remote-sites](2026-10-17-remote-sites.md) | Reaching rigs at another location through a paired remote over a tunnel, with every decision staying in Commander. |
| [device-file-browser](2026-10-17-device-file-browser.md) | The operator's file browser over managed ASIAIRs, and how it stays out of the harvester's way. |
| [asiair-hardware-notes](2026-10-17-asiair-hardware-notes.md) | The ASIAIR's observed behaviour: the numbered hardware findings (H1–H13, with gaps), shares and layout, empty versus absent media, the discovery and control protocols, clock behaviour, the FITS headers it writes, and the SMB1 client behaviours it forces. |
| [features](2026-10-17-features.md) | Self-contained features: FITS previews, astrometry, plate solving, the live transfer feed, next-frame prediction and device clock sync. |

Metric names and their meanings are in `docs/metrics.md`. The tests that guard each invariant
are mapped in the coverage files under `test/`.

**One home per fact.** Each invariant series, hardware fact and glossary term has exactly one
home, and every other document links to it rather than restating it. Hardware facts live in
asiair-hardware-notes and are cited by H-number. The alert catalogue is architecture §10. The
index of invariant series is [delete-safety §7](2026-10-17-delete-safety.md).

**Citing a section.** Section numbers are stable anchors.

- Within `docs/design/`, a document cites "routing-and-filing §9.3" and links the file.
- Code comments cite `design <slug> §N.N`, where the slug is the filename without its date
  prefix and `.md`: `design frame-lifecycle §9.2`.
- Markdown elsewhere in the tree cites the path plus the section:
  `docs/design/2026-10-17-library-reconciliation.md` §5.
- Identifiers unique across the tree are cited bare (H5, P2, INV-4, INV-M2, INV-N4, A1, B1,
  C1, D1). Every other series is qualified by its document: "design library-reconciliation
  I26", "design remote-sites AC27", "design architecture §8.2 invariant 4".
